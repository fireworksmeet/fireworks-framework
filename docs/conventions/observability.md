# 可观测性

> 定位：日志（级别、内容、降噪）、指标、链路、健康检查。
> 边界：测试策略见 `testing.md`；异常与错误码见 `api.md` §四；框架提供的日志 / 链路 / 导出能力见 `../capabilities.md`（配置项以各 starter 的 `README.md` 为准）。
>
> 规范级别：【强制】违反即视为代码问题；【推荐】默认遵守；【禁止】原则上不得使用；【说明】背景解释。

# 一、日志

## 1.1 级别定义（告警阈值只设在 ERROR）

【强制】级别的唯一判据是「**谁需要为此做什么**」，而非主观上的"严重程度"。

| 级别 | 定义 | 谁行动 | 是否告警 |
| --- | --- | --- | --- |
| **ERROR** | 当前流程**已失败**、功能受损，必须人工介入 | 值班工程师，立即 | **是** |
| **WARN** | 出现**非预期**情况，但可恢复 / 可降级 / 已兜底，主流程未中断 | 团队，巡检与趋势分析 | 否 |
| **INFO** | 系统**按预期运转**的关键里程碑（生产默认级别） | 无人（供业务分析与回溯） | 否 |
| **DEBUG** | 面向开发的细粒度过程信息（生产默认关闭） | 开发，排查时临时开启 | 否 |

- 【强制】**告警阈值只设在 ERROR**。
- 【强制】WARN **不触发告警**，可放心用于"非预期但可容忍"的场景。
- 【禁止】为了"避免告警"而把 WARN 降级为 INFO——那会让异常淹没在正常业务流水里，等于丢失信号。
- 【禁止】在 ERROR 记录无需人工介入的问题——会造成告警疲劳，最终导致真故障被忽视。
- 【推荐】ERROR 触发实时告警；WARN 做趋势聚合与周报；INFO 用于业务指标统计。

## 1.2 级别选择规则

【强制】判定顺序（逐条问，命中即停）：

1. 流程是否**已失败**、功能是否**受损**？→ **ERROR**
2. 是否**非预期**，但被恢复 / 降级 / 兜底？→ **WARN**
3. 是否只是**正常业务流转**？→ **INFO**
4. 是否只是**排查细节或高频噪声**？→ **DEBUG**

常见场景对照：

| 场景 | 级别 |
| --- | --- |
| 未捕获异常、核心依赖彻底失败、数据不一致、资金类操作失败、定时任务失败 | ERROR |
| 容器层 5xx（无异常对象，容器自身错误） | ERROR |
| 参数校验不通过、鉴权失败（401 / 403）、业务规则不满足导致的请求失败（余额不足、库存不足、重复提交） | WARN |
| 重试后成功、降级返回兜底数据、慢请求、连接池水位告警 | WARN |
| 应用启动 / 关闭、配置加载、定时任务起止、重要业务状态流转 | INFO |
| 访问日志（`fireworks-webmvc` 内置 LogBook 统一输出，logger 为 `org.zalando.logbook.Logbook`） | TRACE（框架注入，业务不选） |
| 入参出参、SQL 与参数、缓存命中、分支走向、算法中间态 | DEBUG |
| 404 路由不存在、高频重复的客户端错误 | DEBUG |

> 【说明】"用户输入参数错误"用 **WARN** 的原则是：**ERROR 只记录系统逻辑错误、异常或违反重要业务规则，其他错误归 WARN**。
>
> 【说明】访问日志属高频输出，但对生产排查（还原请求现场、定位慢请求）有独立价值，故不受"高频即 DEBUG"的一般规则约束。
> 它由 `fireworks-webmvc` 内置的 LogBook 统一输出到独立 logger，级别 TRACE 是库的既定行为、由框架注入；
> **必须**分流到独立 appender，并按需采样或收紧 body 策略，不与业务日志混排。

## 1.3 降噪要求

- 【强制】WARN 及以上**不得无节制输出**：高频场景必须**降噪**，而不是靠降低级别掩盖问题。
- 【推荐】降噪手段：精简日志内容（只记字段名与原因，不打印完整请求参数）；按接口采样或限速；依赖聚合统计（如"参数校验失败 Top 接口"）而非逐条人工翻看。
- 【禁止】在循环体、高频路径中无条件打印 INFO 及以上日志。

## 1.4 日志内容

- 【强制】关键请求必须具有 traceId / requestId。
- 【说明】框架通过 `fireworks-tracing`（由 `fireworks-webmvc` 默认引入）提供 Micrometer Tracing（OTel 桥接），日志关联段默认取 `traceId` / `spanId`；改用 Agent 探针（OTel 等，键多为 `trace_id` / `span_id`）时必须覆盖 `logging.pattern.correlation`，否则关联段恒为空且**不报错**。
- 【强制】HTTP 访问日志统一由 `fireworks-webmvc` 内置的 LogBook 输出，业务**禁止**自建访问日志 Filter / Interceptor / 切面。
- 【强制】日志必须包含足够的上下文，例如 userId、业务单号、请求 ID。
- 【禁止】打印密码、Token、Cookie、完整身份证号、银行卡号等敏感信息。
- 【强制】**ERROR 级必须保留异常堆栈**，禁止只打印 `e.getMessage()`：

```java
// 正确
log.error("create order failed, userId={}, orderId={}", userId, orderId, e);
// 错误：丢失堆栈，无法定位
log.error("create order failed: {}", e.getMessage());
```

- 【强制】WARN 可视情况省略堆栈（高频场景省略，避免日志体积膨胀）；INFO / DEBUG 无需堆栈。
- 【禁止】不要依赖日志作为数据库审计的**唯一**来源。

# 二、指标与链路

【强制】生产服务至少具备四类能力：**日志 Logs、指标 Metrics、链路 Traces、健康检查 Health**。

- 【强制】核心 API 必须能通过 traceId 定位**完整调用链**。
- 【强制】跨线程 / 跨异步边界的任务必须显式传递链路上下文，否则链路会在异步边界断裂。
  框架由 `fireworks-tracing` 注册容器中唯一的 `ContextPropagatingTaskDecorator` 自动完成：`@Async` 与
  `TaskExecutorUtil` 构建的线程池开箱即用；自行 `new Thread` / 自建 `ExecutorService` 不在覆盖范围内。
- 【推荐】把数据库慢查询、HTTP Client、MQ 消费纳入监控。
- 【推荐】关键业务量与失败量以**指标**表达，而不是靠日志逐条计数（日志只作为下钻手段）。
- 【推荐】健康检查区分"进程存活"与"依赖可用"，避免依赖不可用时被调度器反复重启。
