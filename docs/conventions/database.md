# 数据库设计规范

> 定位：表结构、字段类型与命名、索引与约束、SQL 写法、写路径、迁移与变更安全。
> 边界：SQL 书写与 MyBatis 约定见 `mybatis.md`；对象转换见 `spring-boot.md` §3.5；分层与事务边界见 `spring-boot.md`；幂等见 `idempotency.md`；最终一致性与补偿见 `reliability.md`。
>
> **支持矩阵：PostgreSQL 12+ / MySQL 8.0.1+。** 正文以**规则**为主，所有方言差异集中在文首的方言差异总表，正文只在必要处提示。
>
> 规范级别：【强制】违反即视为代码问题；【推荐】默认遵守；【禁止】原则上不得使用；【说明】背景解释。

| 14 | 分区 | 声明式分区 | `PARTITION BY RANGE` |

- 【强制】方言专属能力即使存在（如 #13 的 MySQL 原生自动更新），本项目**一律不使用**，见 §八。
- 【说明】#2 的取舍是"能否表达**绝对时刻**"，而非"用哪个类型"，详见 `../decisions/0002-audit-fields-and-time-type.md`。

# 一、规范优先级与设计原则

## 1.1 优先级

规则冲突时按此顺序执行：

1. 所用数据库（PostgreSQL / MySQL）的官方语义与限制
2. 本文档
3. 项目架构 / 业务约束
4. 阿里巴巴《Java 开发手册》的通用数据库规范
5. 个人编码习惯

## 1.2 核心原则

- **数据正确性优先于查询便利性**：唯一性、状态合法性、金额精度等约束必须尽可能由数据库保证。
- **结构化数据优先于 JSON**：核心业务字段必须使用明确列，不得把数据库设计成 JSON KV 仓库。
- **索引服务于真实查询**：不为"以后可能会查"建索引，也不为单条 SQL 机械建索引。
- **先设计查询，再设计索引**：索引由真实的 `WHERE`、`JOIN`、`ORDER BY` 与数据分布共同决定。
- **应用层维护业务关系，数据库维护数据完整性**：不使用物理外键，关系由业务代码与约束共同保证（见 §4.1）。
- **禁止为了统一而统一**：字段类型、索引、冗余、软删除由业务语义决定。
- **所有不可逆操作都必须可审查**：生产环境的数据订正、删除、迁移必须具备明确的执行范围与回滚方案。

# 二、设计流程

## 2.1 需求分析

设计表之前先明确：实体是什么、实体间关系、哪些是核心业务属性、哪些允许为空、哪些必须唯一、哪些存在状态流转、哪些需要排序筛选范围查询、哪些高频写、哪些高频读、数据生命周期、是否允许逻辑删除、是否有数据隔离要求。

## 2.2 查询场景先行

【强制】先列出主要 SQL 访问模式，再据此设计索引：

```text
查询用户详情：WHERE id = ?
查询手机号：  WHERE phone = ? AND deleted_at IS NULL
查询用户列表：WHERE status = ? ORDER BY created_at DESC LIMIT ?
```

## 2.3 数据量预估

必须考虑：当前数据量、每日新增、峰值写入、三年后数据量、冷热数据、大字段、是否可能达到百万 / 千万级。

【禁止】仅根据当前数据量设计数据库。

## 2.4 设计评审

【强制】新增或重大修改表结构必须逐条通过 §十七 的评审 Checklist，不以口头确认代替。

## 2.5 SQL 验证

【强制】重要 SQL 必须在设计阶段用接近真实的数据量验证执行计划（命令见 方言表 #9），不能留到上线后再发现。

> 需要验证的场景、关注指标与慢 SQL 分析流程见 §14。

【禁止】把另一方言的执行计划判据直接套用到当前数据库。

# 三、建表规范

## 3.1 表命名

- 【强制】全小写蛇形命名（`snake_case`），**禁止**大驼峰 / 小驼峰。
- 【强制】使用单数名词。
- 【强制】禁止使用数据库保留字作表名（判定方式见 方言表 #11）。
- 【禁止】无实际语义的表名：`data`、`info`、`record`、`table1`。
- 【推荐】优先采用 `业务实体`，确有必要时才用 `业务_用途`。

### 3.1.1 前缀语义

前缀**必须承载明确语义**，不得当作填充词：

| 前缀 | 语义 | 示例 |
| --- | --- | --- |
| `app_` | C 端（客户端）业务 | `app_user`、`app_user_login_log` |
| `admin_` | B 端（管理后台）业务 | `admin_user`、`admin_role` |
| 无前缀 | 通用能力 / 基础数据 / 组件表 | `dict_type`、`agreement`、`city` |

- 【禁止】使用 `sys_` 作为通用前缀；基础数据表（字典、行政区划、行业分类等）不加前缀（`city` 而非 `sys_city`）。
- 【强制】关联表前缀与主体表**完全一致**：主体 `app_user` → `app_user_like`（而非 `user_like`），避免"指哪一端用户"的歧义。
- 【强制】B 端 / C 端成对出现的表命名对称：`admin_user` / `app_user`。

## 3.2 字段命名

- 【强制】全小写蛇形命名，禁止驼峰。
- 【强制】禁止使用保留字。
- 【强制】见名知意；【禁止】`a`、`b`、`flag1`、`type2` 等无意义名称。

## 3.3 保留字

【强制】禁止把完全保留字用作表名 / 列名。典型：`user`、`select`、`order`；`status` 不是保留字，可正常使用。

【说明】两种方言的保留字集合**不同**（判定见 方言表 #11）。当某个词是否适合作标识符有争议时，**换一个更明确的业务名称**，而不是依赖转义。

## 3.4 主键

- 【强制】业务表默认使用 `BIGINT` 主键。
- 【强制】主键生成方式按 方言表 #1；**禁止**使用 `SERIAL` / `BIGSERIAL`。
- 【强制】PostgreSQL 使用 `GENERATED BY DEFAULT AS IDENTITY`（而非 `ALWAYS`）：默认由序列生成，同时允许迁移 / 订正时显式指定 id。
- 【强制】主键约束显式命名 `pk_<表名>`，**禁止**依赖自动生成的默认名。

```sql
-- PostgreSQL
id BIGINT GENERATED BY DEFAULT AS IDENTITY,
CONSTRAINT pk_app_user PRIMARY KEY (id)

-- MySQL
id BIGINT NOT NULL AUTO_INCREMENT,
CONSTRAINT pk_app_user PRIMARY KEY (id)
```

- 【强制】业务代码 `INSERT` **禁止显式指定 `id`**。
- 【强制】迁移 / 订正 / 导入中手动指定了 id 后，**必须把自增序列对齐到当前最大 id**，否则后续自动生成的 id 会冲突：

```sql
-- PostgreSQL
SELECT setval(pg_get_serial_sequence('app_user', 'id'),
              GREATEST((SELECT max(id) FROM app_user), 1));

-- MySQL
ALTER TABLE app_user AUTO_INCREMENT = <max(id) + 1>;
```

### 3.4.1 何时使用 UUID

仅当以下场景明显需要时：ID 出现在**无鉴权的访问路径**上、多节点离线生成、跨库合并需全局唯一、业务明确要求。

【禁止】为了"看起来更高级"而统一改成 UUID。

### 3.4.2 对外标识的选型

对外标识有两种，**不可随意互换**：

| 类型 | 形态 | 例子 |
| --- | --- | --- |
| **有序业务编号** | `xxx_no`，可读、可排序、连续可枚举 | `order_no`、`user_no` |
| **不可枚举标识** | UUIDv7 / ULID，无业务含义、不可预测 | `file_key` |

【强制】选型判据是**该标识出现的访问路径上的鉴权强度**，而非标识本身的形态：

| 路径鉴权强度 | 可枚举编号的后果 | 结论 |
| --- | --- | --- |
| 强（登录态 + 归属校验） | 存在性探测、数量泄露 | ✅ 可用有序编号 |
| 弱 / 无（缓存直出、公开接口、分享链） | **直接获取内容** | ❌ 必须不可枚举 |

【说明】"可枚举"的危害只有两类——**存在性探测**与**数量泄露**；"拿到内容"是**路径无鉴权**导致的，与标识是否可枚举无关。有序编号的收益在于**服务人的流程**（客服沟通、对账排序、分库路由、凭证嵌入）；若某标识**没有人工可读需求**，就没有理由牺牲不可枚举性。

【强制】使用有序编号的前提（缺一不可）：

1. 该路径**必须有鉴权**（登录态 + 归属校验），不得出现在无鉴权的公开路径上；
2. **必须有风控限流**，防批量扫描；
3. **对外编号必须与内部主键解耦**（内部 `id` 不外露），否则编号规则无法演进。

【强制】标识的**生命周期越长，越应按"无鉴权路径"从严处理**——可枚举的风险 = 枚举窗口 × 单次收益。永久有效的标识（如逻辑 URL 中的 `file_key`）必须不可枚举。

【推荐】有序编号做"**有序但猜不准**"处理：`时间前缀 + 分片位 + 加盐 / 随机段 + 校验位`。

【强制】C 端接口默认不对外暴露数据库自增 ID；对外标识使用无语义外部编号（`xxx_no`）或不可枚举标识。

【禁止】为了防枚举把全库主键统一改成 UUID——数据库层保持 `BIGINT` 主键不变，可枚举性问题由 API 层解决（连续自增 ID 会泄露业务量）。

> API 层的对外标识规则见 `api.md` §7.3；本节讲**数据库视角**的标识选型。

## 3.5 审计字段

【强制】业务表默认包含：

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
```

（MySQL 为 `TIMESTAMP`，见 方言表 #2。）

- `created_at`：记录创建时间。
- `updated_at`：**记录最后一次任何写操作的时间**，包含业务字段修改、状态流转与逻辑删除；由**应用层主动维护**，完整写路径、为什么不交给数据库、防遗漏机制均见 §8.3。
- 【推荐】不强制所有表增加 `created_by` / `updated_by`，确有审计需求再加。

> 详见 `../decisions/0002-audit-fields-and-time-type.md`。

## 3.6 时间字段

| 语义 | 类型 | 示例 |
| --- | --- | --- |
| **时间点**（真实发生的时刻） | 绝对时刻列（方言表 #2） | `created_at`、`published_at`、`expired_at`、`paid_at`、`last_login_at` |
| **业务日期**（只关心哪一天） | `DATE` | `birthday`、`settlement_date`、`holiday_date` |
| **一天中的时间**（不关心日期） | `TIME` | 营业时间、每日提醒时间 |

【强制】生日等业务日期**不得**使用绝对时刻列——`1995-11-18` 不应因用户所在时区发生日期偏移。

### 3.6.1 时区约定

- 【强制】应用连接必须**显式固定会话时区**（如 JDBC 连接参数指定 UTC），禁止依赖数据库 / 服务器默认时区。
- 【强制】绝对时刻列在 Java 侧映射为 `Instant`。
- 【禁止】用字符串存储带本地时区偏移的时间。

### 3.6.2 时间字段的"计算位置"

【强制】由**技术时间戳**还是**业务时间**决定其计算位置：

| 类别 | 示例 | 计算位置 |
| --- | --- | --- |
| **技术时间戳** | `created_at`、`updated_at` | 数据库 `CURRENT_TIMESTAMP` 或框架自动填充 |
| **业务时间** | `expired_at`、活动结束时间、`xxx_deadline` | **Java 业务代码计算后作为参数传入** |

【强制】禁止在 SQL 中用 `CURRENT_TIMESTAMP + INTERVAL '...'` 表达**业务规则**的时长：

```sql
-- 正确：Java 侧算好传入
VALUES (#{idempotentKey}, #{bizType}, #{expiredAt})

-- 禁止：业务时长散落在 SQL 中
VALUES (#{idempotentKey}, #{bizType}, CURRENT_TIMESTAMP + INTERVAL '30 days')
```

【说明】写在 SQL 里会散落到多处、无法单元测试、受会话时区影响，且违反"业务逻辑不写入数据库"（见 §六）。

## 3.7 字符串类型

- 【禁止】为"性能"使用 `CHAR(n)`。
- 【建议】有限长度字符串使用 `VARCHAR(n)`；长度本身无业务约束的正文使用 `TEXT`。
- 【禁止】为限制长度而盲目设置极小长度。
- 【说明】两种方言下 `VARCHAR(n)` 与 `TEXT` 的底层存储机制都相近，不应为性能机械拆分。

## 3.8 数值类型

- 【强制】金额、积分、计费数量等要求精确计算的字段使用 `NUMERIC(p, s)`（MySQL 同语法）。
- 【禁止】金额使用 `REAL` / `FLOAT` / `DOUBLE`。
- 整数选择：`SMALLINT`（枚举、有限状态值）、`INTEGER`（普通整数）、`BIGINT`（主键、大数量、累计计数、外部 ID）。

## 3.9 布尔字段

### 3.9.1 适用场景

【强制】判据是**业务语义**，不是"当前只有几个值"：

- **属性语义**（描述静态属性：默认、可见、启用、开关）→ `is_xxx` 布尔列。
- **流程 / 生命周期语义**（审核、认证、激活等存在流转过程）→ **即使当下只有两个值，也建模为 `status SMALLINT`**。

【说明】`is_verified`（是否认证）是典型"伪二值"：认证通常存在"待审核 / 已通过 / 已驳回"，应建模为 `verify_status`。

### 3.9.2 命名

- 【强制】布尔列使用 `is_` 前缀：`is_enabled`、`is_visible`、`is_default`。
- 【禁止】`enabled`、`visible`、`flag`；`status` 不属于布尔语义。

### 3.9.3 Java 侧映射

【强制】数据库列可用 `is_enabled`，Java 属性不必带 `is` 前缀，但**必须显式映射**：

```java
private Boolean enabled;
```

```xml
<result property="enabled" column="is_enabled"/>
```

【说明】这样同时保住数据库命名语义与 Java Bean 兼容性（避免序列化字段名与预期不符）。

## 3.10 状态字段与枚举

- 【强制】多值互斥状态或明确状态机使用 `status SMALLINT NOT NULL`；并识别"伪二值"（见 §3.9.1）。
- 【推荐】表达生命周期 / 处理状态 / 审核状态统一优先用 `status`。
- 【强制】同一张表存在多个状态维度时用 `xxx_status` 区分（`audit_status`、`card_status`）；单状态表统一只用 `status`。
- 【禁止】同语义下混用 `enabled` / `valid` / `visible` / `state` / `status`。
- 【强制】Java 枚举的数据库值统一用 `SMALLINT` 保存；**禁止**保存枚举名（`'DRAFT'`、`'NORMAL'`）。
- 【强制】枚举 `code` 必须稳定：已上线的 `code` 禁止改语义、禁止复用；`code` 不从 `0` 开始（统一从默认 `10` 起），相邻值预留间隔（默认 `10`）。
- 【推荐】枚举项多或预期扩展频繁时，起始值与间隔放大为 `100`。
- 【禁止】依赖 Java `ordinal()`，必须显式定义 `code`。

> 完整决策（含"预留间隔是新增枚举值兼容的前提"）见 `../decisions/0001-enum-stored-as-smallint.md`。

## 3.11 字段注释

- 【强制】核心业务字段必须有注释；枚举字段必须注明**完整映射**：

```sql
-- PostgreSQL
COMMENT ON COLUMN app_user.status IS '用户状态：10-禁用，20-正常，30-锁定，40-注销';

-- MySQL（内联）
status SMALLINT NOT NULL DEFAULT 20 COMMENT '用户状态：10-禁用，20-正常，30-锁定，40-注销',
```

需特别关注的字段：`status`、`type`、`category`、`amount`、`deleted_at`、时间边界字段、来源字段、业务唯一编号。

## 3.12 NULL 与默认值

- 【强制】能明确表示"必有值"的字段使用 `NOT NULL`；不要因为"Java 可以是 null"就把所有字段设计成 nullable。
- 【强制】`NULL` 的语义必须明确（`birthday IS NULL` = 未填写）。若"未填写"与"未知"是两种语义，需单独建模，而不是依赖 `NULL` 猜测。
- 【禁止】为避免 `NULL` 而把字符串默认成空串、数字默认成 0：

```text
未填写手机号 != 空字符串手机号
未知金额     != 0 元
```

## 3.13 逻辑删除

- 【强制】逻辑删除字段统一为 `deleted_at`（可空绝对时刻列）：`NULL` = 未删除，非空 = 删除时间。
- 【禁止】使用 `is_deleted`、`deleted`、`deleted_flag` 等等价替代（唯一例外见 §十的 MySQL 唯一约束配套列）。
- 【推荐】并非所有表都需要软删除：用户核心数据、订单、支付记录、审计记录、关键业务关系通常需要保留历史；纯缓存、临时任务、可重建数据未必需要。

> 专项规范见 §十；决策见 `../decisions/0003-soft-delete-and-unique-constraint.md`。

## 3.14 JSON 列

- 【强制】PostgreSQL 统一使用 `JSONB`（不使用 `JSON`），MySQL 使用 `JSON`。
- 【说明】JSON 列只用于：非固定结构的扩展属性、配置项、第三方接口原始响应快照、不需要强约束的业务扩展字段。
- 【禁止】用 JSON 保存核心业务属性（如把 `nickname` / `gender` / `birthday` 塞进 JSON）——若这些字段是核心查询条件，必须是正规列。
- 【说明】高频 JSON 查询需针对实际 SQL 建索引（PostgreSQL 用 GIN 或表达式索引，MySQL 用生成列 + 索引）；**禁止"看到 JSON 就建索引"**。

## 3.15 文件与二进制存储

- 【强制】图片、视频、附件等二进制内容统一存对象存储，数据库**只保存逻辑 URL**、格式、大小等元数据。
- 【强制】承载文件的字段统一命名为 `xxx_url`（`avatar_url`、`cover_url`）；**禁止** `xxx_key` / `xxx_object_key`（存储实现细节），禁止裸名（`avatar`，语义不明）。
- 【禁止】保存对象存储的物理地址、`object_key`、桶名。
- 【禁止】使用二进制大对象列（`BYTEA` / `BLOB`）保存业务文件；仅允许用于极小的必要二进制数据（如密钥材料），且必须经评审。
- 【说明】需要历史可还原的业务数据（如审核照片），保存业务快照引用与元数据，不复制文件本体。

# 四、表关系与数据完整性

## 4.1 不使用物理外键

【强制】业务表不创建物理 `FOREIGN KEY`。原因：大规模写入时增加约束检查成本、复杂迁移更难控制、跨服务跨库无法使用、业务删除 / 归档通常不适合数据库级联。

【说明】"不使用外键"不等于"不维护关系"，关联关系仍必须通过业务代码、唯一约束、`NOT NULL`、`CHECK`、唯一索引、数据一致性任务共同保证。

## 4.2 一对多

子表使用 `<主表>_id BIGINT NOT NULL` 关联主表；索引按实际查询模式建立，组合顺序与排序处理见 §5.4。

## 4.3 多对多

【强制】使用关系表，**禁止**在实体表里塞逗号分隔 ID（`user.like_user_ids = '1,2,3,4'`）。

## 4.4 数据冗余

【强制】允许适当冗余，但必须记录：冗余字段来源、谁是主数据源、谁负责同步、同步失败如何修复。

> 订单、支付等历史数据的快照式冗余见 §11.2。

## 4.5 数据隔离

- 【说明】若当前为单租户应用，业务表不设 `tenant_id`。
- 【强制】若引入多租户 / 多商户，必须先通过 ADR 评审租户模型（共享表 + `tenant_id` / 独立 schema / 独立库）再统一实施；**禁止**个别表私自添加 `tenant_id` 形成"半套多租户"。

# 五、索引与约束

## 5.1 命名

【强制】索引 / 约束显式命名并携带完整表名，保证数据库内全局唯一：

```text
pk_<表名>                    -- 主键约束
uk_<表名>_<列或列组合>        -- 唯一约束 / 唯一索引
idx_<表名>_<列或列组合>       -- 普通索引
```

- 【强制】主键与唯一约束必须使用 `CONSTRAINT` 子句显式命名，**禁止**依赖默认名。
- 【说明】长组合索引注意标识符长度上限（方言表 #12），超长时使用语义化缩写。

## 5.2 唯一性必须由数据库保证

【强制】业务上唯一的字段或组合字段必须建立唯一约束 / 唯一索引。

```text
错误：先 SELECT 检查是否存在 → 不存在再 INSERT   （并发下仍会插入重复数据）
正确：建立唯一约束，由应用层捕获唯一约束冲突并友好处理
```

## 5.3 组合索引

【强制】索引顺序由**查询谓词、排序方式、选择性与数据分布**共同决定，不得机械套用"区分度最高放最左"。

```sql
-- WHERE user_id = ? AND status = ? ORDER BY created_at DESC  → (user_id, status, created_at DESC)
-- WHERE status = ? ORDER BY created_at DESC                  → (status, created_at DESC)
```

## 5.4 排序、范围查询与分页

```sql
-- WHERE user_id = ? ORDER BY created_at DESC LIMIT 20
CREATE INDEX idx_order_main_user_id_created_at
    ON order_main (user_id, created_at DESC, id DESC);
```

- 【推荐】游标 / 分页场景把 tie-breaker 主键一并纳入索引，减少额外排序成本。
- 【说明】索引中的范围条件可能限制后续列的排序 / 筛选能力。`(user_id, created_at, id)` 不必然同时完美满足过滤与排序，必须用执行计划验证（方言表 #9）。

## 5.5 部分索引 / 条件索引

【推荐】查询只关注少量状态时优先用部分索引降低索引大小：

```sql
-- PostgreSQL
CREATE INDEX idx_order_main_processing
    ON order_main (user_id, created_at DESC)
    WHERE status IN (20, 30) AND deleted_at IS NULL;
```

- 【强制】查询条件必须能匹配索引谓词。
- 【说明】**MySQL 不支持部分索引**（方言表 #5）：只能建普通复合索引（把过滤列放到最左），或改用其他建模方式。

## 5.6 表达式索引 / 前缀索引

```sql
-- PostgreSQL：表达式索引
CREATE INDEX idx_app_user_lower_email ON app_user ((lower(email)));
-- 查询必须使用兼容表达式
WHERE lower(email) = lower(?)

-- MySQL：原生前缀索引
CREATE INDEX idx_xxx_prefix ON example (code(20));
```

- 【禁止】把某一方言的前缀 / 表达式索引语法迁移到另一方言。
- 【强制】普通 B-Tree 索引下，`WHERE` 中对**列**使用函数会导致索引失效，用范围查询替代：

```sql
-- 禁止：索引失效
WHERE DATE(created_at) = '2026-08-17'

-- 正确：范围查询
WHERE created_at >= '2026-08-17 00:00:00' AND created_at < '2026-08-18 00:00:00'
```

## 5.7 模糊查询

- 【禁止】在大表上无评估地使用左模糊 / 包含模糊：`WHERE nickname LIKE '%张%'`（普通 B-Tree 索引通常无法有效支持）。
- 【推荐】前缀匹配可用 `LIKE '张%'` 并结合合适的索引方案。
- 【说明】若业务确实需要任意位置关键词搜索、中文分词、多字段全文搜索（如单输入框同时搜订单号 + 商品名 + 收货人），应**单独设计搜索架构**（全文检索 / 独立搜索服务），而不是不断给业务表加 B-Tree，也不应写成多个 `OR ... LIKE` 再靠 `DISTINCT` 去重。

## 5.8 覆盖索引与数量控制

- 【说明】每增加一个索引都会带来磁盘空间与写入、维护成本。不要为"覆盖"而把大量字段塞进索引，仅当 SQL 高频、数据量大且收益明确时，才考虑把少量列加入索引（如 PostgreSQL `INCLUDE`）。
- 【禁止】一个 SQL 一个索引；一个字段既建单列索引又出现在多个冗余组合索引中而无理由；长期不使用的索引继续保留。
- 【强制】新增索引必须说明它服务哪些核心查询。

## 5.9 CHECK 约束

- 【推荐】简单且稳定的规则可使用 `CHECK`：`CHECK (amount >= 0)`。
- 【说明】枚举状态若值集合长期稳定也可使用 `CHECK`；但状态持续扩展且由 Java 枚举控制时，可只由应用层管理，并在文档中明确值域。
- 【禁止】把复杂业务规则硬编码成 `CHECK`（涉及多表、外部服务、频繁变化的状态机）。

# 六、SQL 规范

## 6.1 禁止 `SELECT *`

【强制】必须明确字段列表。原因：降低网络传输、避免读取无用大字段、降低映射耦合、防止表结构新增字段后 SQL 行为变化。

## 6.2 NULL 判断

【强制】统一使用 `IS NULL` / `IS NOT NULL`，**禁止**把 `NULL` 与 `=` / `<>` 混用判断。

## 6.3 聚合函数

- 【推荐】`COUNT(*)`；需要时使用 `COALESCE(SUM(amount), 0)`。
- 【禁止】使用某一方言的专属函数写通用 SQL（如把 MySQL 的 `IF()` / `ISNULL()` 搬到 PostgreSQL）；跨方言项目统一用 `COALESCE` 等标准函数。

## 6.4 大 `IN` 集合

【说明】不存在通用的"绝对 1000 条上限"，应根据 SQL 长度、参数数量、执行计划、数据量、网络传输、执行时间综合评估（接口入参上限另见 `api.md` §五）。

【强制】ID 集合很大时不得把几十万 ID 拼进 `IN (...)`，应改用临时表、`VALUES`、批量导入后 `JOIN` 或更合理的查询条件。

## 6.5 分页

【强制】任何分页查询必须明确排序条件；排序字段末尾**追加主键作为 tie-breaker**（如 `ORDER BY created_at DESC, id DESC`）。不加 tie-breaker 时，排序字段值相同的行在**不同页之间顺序不稳定**，会导致翻页出现重复或漏行。

### 6.5.1 默认：Keyset（游标）分页

【推荐】列表接口优先使用 Keyset Pagination，特别是大表：

```sql
SELECT id, created_at, status
FROM order_main
WHERE user_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

- 【强制】游标列必须与 `ORDER BY` **完全一致**；索引建议建成 `(user_id, created_at DESC, id DESC)`。
- 【强制】游标列允许 `NULL` 时 row-value 比较语义不符预期，应先过滤 `NULL` 或改用展开写法：

```sql
AND (created_at < ? OR (created_at = ? AND id < ?))
```

### 6.5.2 OFFSET 分页与 COUNT 取舍

- 【强制】深分页禁止无限制使用（`OFFSET 1000000`）。
- 【推荐】确需深分页且必须保留页码语义时，先分页取 ID，再查询完整数据（延迟关联）。
- 【强制】不要默认每次都执行昂贵的 `COUNT(*)`，须按产品需求评估：是否真的需要精确总数、是否只需要"是否有下一页"、是否允许近似数量、是否可以缓存统计结果。

## 6.6 触发器、存储过程与视图

- 【禁止】把业务逻辑写入触发器、存储过程、自定义函数：难以版本控制与调试，阻碍迁移与逻辑复制，且代码库外的逻辑对评审与 AI 不可见。
- 【禁止】用触发器 / 扩展维护 `updated_at` 等审计字段（含 MySQL 原生 `ON UPDATE CURRENT_TIMESTAMP`），理由见 §8.3.1。
- 【推荐】只读视图可用于收敛高频复杂查询口径，但必须与表结构同版本管理；物化视图按刷新成本单独评估。

## 6.7 SQL 书写风格

- 【强制】关键字大写：`SELECT`、`FROM`、`WHERE`、`ORDER BY`。
- 【强制】合理换行：`SELECT`、`FROM`、`WHERE`、`ORDER BY` 各占一行。
- 【强制】多表关联使用显式 `INNER JOIN`，而非 `WHERE` 隐式关联。
- 【强制】字段命名使用下划线风格（`real_name`），**禁止驼峰**。

# 七、JOIN 规范

- 【说明】**不采用**"超过三个表禁止 JOIN"这类绝对规则。能否 JOIN 取决于数据规模、关联条件、索引、返回数据量、执行计划与业务复杂度。
- 【强制】关联字段类型必须一致（两侧同为 `BIGINT`），否则可能产生隐式类型转换并影响索引使用。
- 【推荐】只判断关联记录是否存在时，优先 `EXISTS`：

```sql
WHERE EXISTS (SELECT 1 FROM order_item oi WHERE oi.order_id = o.id)
```

- 【禁止】用 `DISTINCT` 掩盖一对多 `JOIN` 导致的重复数据——应先确认业务语义是否真的需要 JOIN。

# 八、写路径与事务

## 8.1 事务边界

- 【强制】事务必须围绕一个明确的业务一致性单元。
- 【禁止】把整个请求链路放进长事务；在事务中执行大量无关查询；为"保险"给所有方法加事务注解。
- 【禁止】在事务中调用远程服务，见 §8.2。

> 事务注解的落点见 `spring-boot.md`；跨系统一致性见 `reliability.md`。

## 8.2 事务内不调用慢外部服务

```text
禁止：DB UPDATE → HTTP/RPC 调第三方 → DB COMMIT
推荐：DB 事务（含记录业务结果 / outbox）→ COMMIT → 异步发送
```

【说明】第三方延迟会直接拉长数据库事务持有时间。

## 8.3 `updated_at` 必须由应用层主动维护

### 8.3.1 为什么不使用数据库自动维护

【说明】PostgreSQL 需自建触发器或安装扩展，MySQL 原生支持 `ON UPDATE CURRENT_TIMESTAMP`（方言表 #13）。本项目**一律不使用**，理由：

1. **业务逻辑外置、不可见**：写进数据库后代码库与评审不可见、无法随代码版本化。
2. **迁移与复制受阻**：触发器随 DDL 存在，跨环境迁移、逻辑复制、数据导入导出时行为不一致；扩展在部分托管数据库不允许安装。
3. **性能与可观测成本**：行级触发器对每次 `UPDATE` 产生额外开销，批量更新按行放大，且该开销**不出现在执行计划中**。
4. **语义被动**：无法区分"业务字段真正变更"与"重复写入同一值"，容易刷新出无意义的 `updated_at`（与 §3.5 冲突）。

代价是：**漏写不会报错，数据库也不会兜底**，只会静默产生脏数据，因此必须配合 §8.3.3 的防遗漏机制。

### 8.3.2 写路径全覆盖

【强制】按以下清单逐条执行，禁止遗漏：

| 写路径 | `updated_at` 要求 | 由谁维护 |
| --- | --- | --- |
| `INSERT` | 必须写入（通常等于 `created_at`） | 框架自动填充 / 显式书写 |
| `UPDATE`（条件构造器 / `updateById`） | 必须刷新 | 框架自动填充（引入 MP 粘合层时） |
| `UPDATE`（手写 SQL） | 必须刷新 | 显式 `SET updated_at = CURRENT_TIMESTAMP` |
| 批量 `UPDATE` | 必须刷新 | 显式 `SET updated_at = CURRENT_TIMESTAMP` |
| 状态流转（`SET status = ... WHERE status = 旧值`） | 必须刷新 | 与状态字段同一句 `SET` |
| **逻辑删除** | **必须同时刷新** | 与 `deleted_at` 同一句 `SET` |
| 手工订正 / 迁移 SQL | 必须刷新 | 显式 `SET updated_at = CURRENT_TIMESTAMP` |

- 【强制】手写 SQL **不经过任何自动填充**，不存在兜底：

```sql
UPDATE app_user
SET deleted_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE id = ?
  AND deleted_at IS NULL;
```

### 8.3.3 防遗漏机制

【强制】至少落实其一，用于发现"漏写 `updated_at`"的静默错误：

1. **SQL 静态检查（最推荐）**：CI 中扫描 `db/` 与 `**/resources/mapper/**/*.xml`，凡是涉及带 `updated_at` 列的 `INSERT` / `UPDATE` 必须出现 `updated_at`，否则构建失败。
2. **Code Review 强制核对**：任何手写 `UPDATE` 与逻辑删除逐条核对。
3. **定期巡检（仅作发现手段，不替代应用层）**：巡检"业务字段已变更但 `updated_at` 早于变更时间"的异常数据。

### 8.3.4 禁止整行回写

- 【禁止】**整行回写**：即"查出完整对象 → 修改个别字段 → 整行 `UPDATE` 回去"。
  【说明】该模式的代价：把所有非空列全部 `SET` 一遍（无意义写入），并**放大并发覆盖风险**（把你没读到的字段一起覆盖）。
- 【禁止】用一个"大而全"的更新对象无条件覆盖整行。
- 【强制】"更新哪些列"必须由代码**显式表达**（显式列清单或条件更新），不得依赖隐式的"非 null 才更新"策略。

## 8.4 乐观锁

【推荐】高并发更新存在覆盖问题且**没有天然状态可作守卫**时，增加 `version INTEGER NOT NULL DEFAULT 0`：

```sql
UPDATE app_user
SET nickname = ?, version = version + 1, updated_at = CURRENT_TIMESTAMP
WHERE id = ? AND version = ?;
```

- 【强制】影响行数为 0 时必须按业务规则处理（重试或返回冲突），**禁止忽略返回值**。

## 8.5 悲观锁

【推荐】需要强制串行化关键业务时使用 `SELECT ... FOR UPDATE`，但必须严格控制锁持有时间与查询范围。

【说明】`FOR UPDATE` 只能锁**已存在**的行，无法锁"尚不存在的行"；并发竞态的首选手段是 CAS（见 §九）。

# 九、并发与唯一性

## 9.1 禁止"先查后插"保证唯一

【强制】唯一性一律由数据库唯一约束保证，**禁止**用"先查后插"实现——并发下两侧都会通过检查。写法与理由见 §5.2。

## 9.2 状态变更必须考虑并发

【强制】状态变更必须带**前置状态条件**并检查影响行数（CAS）：

```sql
-- 错误：并发下会把已流转的状态再覆盖一次
UPDATE order_main SET status = 2 WHERE id = ?;

-- 正确
UPDATE order_main
SET status = 2, updated_at = CURRENT_TIMESTAMP
WHERE id = ? AND status = 1;
```

> 补偿场景的三态判定与 CAS 抢占见 `reliability.md` 与 `../decisions/0004-compensation-idempotency-and-race.md`。

## 9.3 幂等

- 【强制】支付、回调、消息消费、订单创建等接口必须设计幂等约束。
- 【强制】落地形式按优先级选择：**业务唯一键 → 幂等表 → 数据库唯一约束兜底**；业务表天然存在唯一标识时直接建唯一约束，不引入额外表。
- 【强制】幂等占位按 方言表 #10 的方言写法，以影响行数判定是否重复；批量去重需拿到"本次真正插入的集合"（PostgreSQL 用 `RETURNING`，MySQL 无 `RETURNING`）。
- 【禁止】"先插入再按 key 查回"来区分新旧。
- 【说明】防篡改与防重放属入口层职责，**不能替代**业务幂等（二者粒度不同）。

> 完整规范见 `idempotency.md`。

# 十、软删除专项

## 10.1 查询

【强制】业务默认查询必须带 `WHERE deleted_at IS NULL`；删除操作必须显式 `SET deleted_at = CURRENT_TIMESTAMP`（**禁止** `UPDATE` 为魔法值）。

【推荐】在 SQL 片段中统一复用该条件，防止遗漏。

## 10.2 唯一约束

需求是"**只有未删除的数据唯一**"，实现方式随方言不同：

```sql
-- PostgreSQL：部分唯一索引
CREATE UNIQUE INDEX uk_app_user_phone ON app_user (phone) WHERE deleted_at IS NULL;

-- MySQL：删除标记列 + 组合唯一索引
--   未删除时恒为 0；删除时置为该行 id
deleted_flag BIGINT NOT NULL DEFAULT 0,
UNIQUE KEY uk_app_user_phone (phone, deleted_flag)
```

- 【说明】**不能**在 MySQL 上简单写 `UNIQUE (phone, deleted_at)`：MySQL 唯一索引把 `NULL` 视为互不相等，未删除行（`deleted_at IS NULL`）之间**不会被约束**，唯一性形同虚设。
- 【说明】MySQL"唯一索引允许多个 `NULL`"这一特性，只在**允许 `NULL` 表示"不参与约束"**时可用（如可空幂等键）；软删除需要的是"未删除时**必须**参与约束"，因此必须引入非空标记列。
- 【强制】`deleted_flag` 只作为唯一约束的配套列存在，**不用于业务查询**（业务查询一律用 `deleted_at IS NULL`）。

> 决策与推导见 `../decisions/0003-soft-delete-and-unique-constraint.md`。

## 10.3 恢复数据

【强制】恢复操作必须明确处理唯一约束冲突：例如恢复用户前，需确认当前未删除数据中是否已存在相同手机号。

## 10.4 软删除不是永久保留

【说明】软删除只是业务层隐藏数据，**不等同于真正的数据保留策略**。对于存在合规、隐私、数据保留周期要求的业务，需要额外设计真正的数据清理机制。

# 十一、审计、日志与快照

## 11.1 业务数据与日志分离

【推荐】不要把操作日志无限塞进业务主表（`app_user` / `app_user_operation_log` 分离）。

## 11.2 快照字段

【推荐】订单、支付等具有历史语义的数据，保存必要快照：商品名称、商品规格、收货地址、价格。

【说明】当前商品数据变化后，历史交易数据仍必须可还原。**快照字段不是"冗余错误"，而是历史数据建模的一部分。**

# 十二、迁移与版本管理

## 12.1 所有结构变更必须可追踪

- 【强制】生产数据库**禁止**手工直接修改后不提交迁移脚本；表结构变更必须进入版本控制。
- 【禁止】改写基线脚本——基线仅用于初始化新环境，生产库后续变更一律走 `migration/`。

```text
db/
├── baseline/                          # 初始建表基线（可执行 DDL，新环境一键初始化）
│   ├── 01_app_user.sql
│   └── 02_app_user_like.sql
└── migration/                         # 增量变更（版本化命名）
    ├── V20260817__create_user_table.sql
    └── V20260818__add_user_status.sql
```

【说明】是否引入迁移工具（Flyway / Liquibase）由团队统一决定；未引入前，增量脚本按上表命名、按版本号顺序人工执行，且执行记录必须可查。

## 12.2 大表加列

【强制】按变更类型选择策略，禁止一刀切套用重流程：

- 新增可空列，或新增带**常量默认值**的列：属元数据级操作（方言表 #8），可直接执行：

```sql
ALTER TABLE app_user ADD COLUMN remark TEXT;
ALTER TABLE app_user ADD COLUMN source SMALLINT NOT NULL DEFAULT 10;
```

- 需要回填历史数据的变更：分阶段执行——加列 → **分批回填（每批独立提交）** → 视需要再加 `NOT NULL` / 约束。
- 修改字段类型、增加唯一约束等**重写表数据或长锁**操作：按「兼容字段 → 双读 / 双写 → 切换 → 回收」分阶段执行，并评估锁影响与回滚方案。

【禁止】一次迁移同时完成所有破坏性操作。

## 12.3 大表建索引

【推荐】生产大表建索引优先使用在线方式（方言表 #7）。

【说明】`CREATE INDEX CONCURRENTLY` 有特殊事务限制（不能在事务块中执行；失败会留下 `INVALID` 索引，需 `DROP` 后重试），迁移工具必须正确配置。

## 12.4 删除字段

【强制】分阶段执行：

```text
停止代码使用 → 观察一段时间 → 确认无读写 → 备份/确认可恢复 → 删除字段
```

【禁止】代码与数据库同时"删字段 + 删代码"一步完成。

# 十三、变更安全与数据订正

## 13.1 高风险操作

以下属高风险：删除表、删除字段、修改字段类型、大范围 `UPDATE` / `DELETE`、大表创建唯一索引、修改唯一约束、大范围回填。

【强制】必须提供：影响范围、执行 SQL、执行顺序、回滚方案、验证 SQL、失败处理方案。

## 13.2 生产环境 `UPDATE` / `DELETE`

- 【强制】执行前**先 `SELECT` 确认影响范围**，确认后再执行：

```sql
-- 1. 先确认
SELECT id FROM app_user WHERE ...;
-- 2. 再执行
UPDATE app_user SET ... WHERE ...;
```

【禁止】在生产环境凭感觉执行无条件 `UPDATE` / `DELETE`。

- 【强制】大批量删除 / 更新**分批执行**（每批 1000~10000，独立提交），**禁止**一次性操作数千万行并长期持有大事务。批次大小按线上负载测试确定，不设全局固定值。
- 【强制】`TRUNCATE` 生产环境默认禁止，仅在明确知道表可整体清空且不影响业务依赖时使用。

## 13.3 DDL 与事务

【强制】执行生产 DDL 前必须确认：锁类型、锁等待影响、是否支持事务、是否支持在线执行、预计执行时间。

## 13.4 数据迁移不得依赖业务猜测

【强制】迁移脚本必须带明确条件：

```sql
-- 正确
UPDATE app_user SET status = 20, updated_at = CURRENT_TIMESTAMP WHERE status IS NULL;

-- 禁止
UPDATE app_user SET status = 20;
```

# 十四、生产性能

## 14.1 性能基线验证场景

【强制】以下情况必须验证核心 SQL 的执行计划：新建 SQL、大表新增查询、新增或修改索引、修改分页方式、增加 `JOIN`、增加复杂 `OR`、新增搜索能力。

## 14.2 必须记录的指标

【推荐】记录 QPS、P50 / P95 / P99、平均执行时间、扫描行数、返回行数、索引命中情况、数据库 CPU、IO、锁等待。

【禁止】只看平均耗时。

## 14.3 慢 SQL 分析流程

```text
发现慢 SQL → 复制真实 SQL → 执行计划分析 → 判断扫描 / 排序 / JOIN / 锁问题
→ 确认数据分布 → 改 SQL 或索引 → 再次对比执行计划 → 线上观察
```

- 【禁止】仅凭"看起来应该会走索引"判断性能。
- 【禁止】仅凭开发库的执行速度判断生产性能。

## 14.4 分区与归档

- 【说明】"500 万行"或"2GB"**不能**作为是否分库分表的机械门槛。真正应关注：单表查询性能、索引大小、清理 / 回收压力、`UPDATE` / `DELETE` 频率、热点竞争、备份与恢复时间、数据生命周期。
- 【推荐】优先考虑 `热数据 → 历史归档 → 必要时再做分区`，而不是一开始就引入复杂分库分表。
- 【说明】当数据天然按时间、租户等维度分段，且单表规模巨大、归档收益明显时，才评估分区（方言表 #14）。

# 十五、推荐建表模板

符合本规范的典型业务表（两种方言）：

```sql
-- PostgreSQL
CREATE TABLE app_user (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY,
    CONSTRAINT pk_app_user PRIMARY KEY (id),
    phone       VARCHAR(32),
    nickname    VARCHAR(32) NOT NULL,
    birthday    DATE,
    status      SMALLINT NOT NULL DEFAULT 20,
    is_visible  BOOLEAN NOT NULL DEFAULT TRUE,
    ext_info    JSONB,
    deleted_at  TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

COMMENT ON COLUMN app_user.status     IS '用户状态：10-禁用，20-正常，30-锁定，40-注销';
COMMENT ON COLUMN app_user.is_visible IS '是否可见：true-是，false-否';
COMMENT ON COLUMN app_user.deleted_at IS '删除时间：NULL-未删除，非NULL-已删除';

CREATE UNIQUE INDEX uk_app_user_phone
    ON app_user (phone) WHERE deleted_at IS NULL;

CREATE INDEX idx_app_user_status_created_at
    ON app_user (status, created_at DESC) WHERE deleted_at IS NULL;
```

```sql
-- MySQL 8
CREATE TABLE app_user (
    id          BIGINT       NOT NULL AUTO_INCREMENT,
    phone       VARCHAR(32)  NULL,
    nickname    VARCHAR(32)  NOT NULL,
    birthday    DATE         NULL,
    status      SMALLINT     NOT NULL DEFAULT 20 COMMENT '用户状态：10-禁用，20-正常，30-锁定，40-注销',
    is_visible  TINYINT(1)   NOT NULL DEFAULT 1   COMMENT '是否可见：1-是，0-否',
    ext_info    JSON         NULL,
    deleted_at  TIMESTAMP    NULL COMMENT '删除时间：NULL-未删除，非NULL-已删除',
    deleted_flag BIGINT      NOT NULL DEFAULT 0,
    created_at  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_app_user PRIMARY KEY (id),
    UNIQUE KEY uk_app_user_phone (phone, deleted_flag),
    KEY idx_app_user_status_created_at (status, created_at DESC)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

# 十六、项目统一约定速查

| 业务语义 | 推荐字段 | 类型 |
| --- | --- | --- |
| 主键 | `id` | `BIGINT` |
| 创建时间 | `created_at` | 绝对时刻列 |
| 更新时间 | `updated_at` | 绝对时刻列 |
| 删除时间 | `deleted_at` | 绝对时刻列，可空 |

| 业务唯一编号 | `xxx_no` | `VARCHAR` |
| 金额 | `amount` | `NUMERIC` |
| 业务日期 | `xxx_date` | `DATE` |
| 时间点 | `xxx_at` | 绝对时刻列 |
| 扩展属性 | `ext_info` | `JSONB` / `JSON` |

【强制】不要把所有字段都设计成 `status`，也不要把所有状态都强行设计成布尔——判据见 §3.9.1 与 §3.10。

# 十七、数据库评审 Checklist

## 表级

- [ ] 表名小写蛇形、单数、非保留字；前缀语义正确（`app_` / `admin_` / 无前缀）
- [ ] 关联表前缀与主体表一致；B/C 端成对表命名对称
- [ ] 是否真的需要软删除
- [ ] 是否评估三年后数据量

## 主键与标识

- [ ] 主键类型合理，默认 `BIGINT` + 方言自增（未用 `SERIAL` / `BIGSERIAL`）
- [ ] UUID 是否确有必要
- [ ] 对外标识的选型是否按**鉴权强度**判断（无鉴权路径必须不可枚举）
- [ ] C 端是否暴露了自增 ID

## 字段

- [ ] 字段名全部 `snake_case`、非保留字、见名知意
- [ ] 核心字段 `NOT NULL`；`NULL` 语义明确；默认值合理（未用空串 / 0 兜底）
- [ ] 金额使用 `NUMERIC`；未使用浮点
- [ ] 时间点用绝对时刻列，业务日期用 `DATE`
- [ ] 布尔列用 `is_` 前缀；流程 / 生命周期语义使用 `status`（未用布尔承载）
- [ ] 多状态维度使用 `xxx_status`；枚举值固定、不从 0 起、预留间隔、有注释
- [ ] JSON 列仅用于非固定结构数据
- [ ] 文件字段命名为 `xxx_url`，未保存物理地址 / `object_key`

## 关系

- [ ] 没有物理外键
- [ ] 多对多使用关系表
- [ ] 冗余字段已定义数据源与同步责任
- [ ] 若涉及多租户，租户模型已经 ADR 评审（未出现"半套多租户"）

## 索引

- [ ] 每个业务唯一字段都有数据库唯一约束
- [ ] 索引命名符合规范，主键 / 唯一约束显式命名
- [ ] 索引来自真实查询；组合索引顺序经过分析；无冗余 / 低价值索引
- [ ] 软删除唯一约束按方言实现（PG 部分索引 / MySQL 删除标记列）
- [ ] 大表建索引使用在线方式并确认事务限制

## SQL

- [ ] 无 `SELECT *`；无无意义 `DISTINCT`
- [ ] `NULL` 使用 `IS NULL`
- [ ] 深分页已评估（优先 Keyset）；`COUNT(*)` 必要性已评估
- [ ] 左模糊 / 包含模糊已评估可行性
- [ ] 大 `IN` 集合已评估
- [ ] JOIN 条件字段类型一致
- [ ] 核心 SQL 已执行执行计划分析

## 写路径与并发

- [ ] 事务范围合理；无长时间远程调用嵌套在事务中
- [ ] 所有手写 `INSERT` / `UPDATE`（含批量、状态流转、迁移脚本）都维护了 `updated_at`
- [ ] 逻辑删除同时更新 `deleted_at` 与 `updated_at`
- [ ] 已落实防遗漏手段（SQL 静态检查 / 定期巡检）
- [ ] 状态变更带前置状态条件并检查影响行数
- [ ] 幂等约束明确（业务唯一键 → 幂等表 → 唯一约束兜底）
- [ ] 必要时使用乐观锁 / 悲观锁，且处理了影响行数为 0 的分支

## 迁移与变更安全

- [ ] 已提供迁移脚本（未改写基线）；变更可回滚或有补偿方案
- [ ] 高风险操作已提供影响范围、执行顺序、验证 SQL、回滚方案
- [ ] 大表操作已评估锁影响；删除字段采用分阶段发布；回填采用批量方式
