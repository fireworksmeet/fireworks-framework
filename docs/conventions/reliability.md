# 可靠性与最终一致性

> 定位：跨进程 / 跨系统的一致性设计——一致性要求定义、事务边界、可靠消息（Outbox）、补偿与对账。
> 边界：**幂等本身**（幂等键、幂等表、执行模型）见 `idempotency.md`；接口契约与演进见 `api.md`；框架提供的可靠消息组件见 `../capabilities.md`。
>
> 规范级别：【强制】违反即视为代码问题；【推荐】默认遵守；【禁止】原则上不得使用；【说明】背景解释。

---

# 一、第一原则

- 【强制】对每一处跨系统交互，先**显式声明一致性要求**（强一致 / 最终一致），再选实现方式；禁止默认两者等价。
- 【强制】强一致只保留在**能被同一个数据库事务覆盖**的范围内。
- 【推荐】其余交互按最终一致设计：本地事务只写"意图"，由异步投递 + 重试 + 补偿收敛。

---

# 二、事务边界

- 【强制】数据库事务只覆盖数据库内部操作：事务内不执行远程调用、不发 MQ（事务落点与自调用陷阱见 `spring-boot.md` §事务）。
- 【强制】提交后需要驱动外部动作时，用**事务提交后**（`AFTER_COMMIT`）触发，而不是在事务内直接调用。
  事务内一旦提交失败，会留下"外部已执行、本地已回滚"的悬挂状态。
- 【禁止】把 Spring `ApplicationEvent` 当**跨进程**可靠消息：它不持久化、不重投、重启即丢，
  跨服务投递统一走 §三 的 Outbox（同进程解耦见 `spring-boot.md` §事件）。

---

# 三、跨服务一致性：统一走 Outbox

- 【强制】需要"业务成功 ⇔ 消息最终会被投递"的场景，统一使用框架的 Outbox。
- 【禁止】在业务侧自研本地消息表、定时扫描投递或双写 MQ 等同类机制——重复建设会导致语义分叉（幂等键口径、补偿语义各不相同）。
- 【说明】Outbox 语义是 **At-Least-Once，不是 Exactly-Once**。"重复执行"是正常运行状态，因此**消费端必须幂等**。

## 3.1 写入

- 【强制】写入必须与业务写操作处于**同一本地事务**：提交则两者都在，回滚则两者都不在。这是该方案唯一的正确性来源。
- 【禁止】在写入前后执行任何远程调用。
- 【说明】消息实例 ID（`event_id`）由框架生成、全局唯一，同一条消息重投时该值不变。
  **一条事件对应一个业务项时**，消费端可直接用它做幂等键；payload 是列表（一条事件含 N 个业务项）时
  必须下沉到业务项粒度，不能拿 `event_id` 兜住整批——否则部分成功部分失败后，重试会被整条拦住，失败项永远无法补偿（见 `idempotency.md` §6.1）。
- 【说明】**不设"业务幂等键"字段**：重复的业务操作会在业务表唯一约束处失败，同一事务里的 outbox 写入随之回滚，不需要 outbox 再兜一层。若某个操作没有业务行可挂唯一键，应在业务侧建幂等记录，而不是给 outbox 加键。
- 【强制】payload 只放**最小上下文**（如 `orderId`）：不得整对象落库；不得写入密码、Token、密钥、证件原文等敏感信息。

## 3.2 投递与重试

- 【强制】投递处理器必须幂等——它可能因重试、超时恢复、进程崩溃重放而被重复执行。
- 【强制】区分可重试与不可重试：连接失败、超时、下游暂时不可用属可重试；参数非法、权限不足、业务状态非法属不可重试，必须显式声明，不要让它白白耗尽重试次数。
- 【强制】超时恢复的时间阈值（`fireworks.outbox.recovery.timeout`）必须**大于**处理器的最长执行时间，
  否则会把正在执行的事件误判为超时并重复投递。
- 【禁止】两层无限重试：Outbox 的职责是"消息是否成功投递"，**业务流程的重试属于编排层**，不要用 Outbox 重试表达业务重试。

## 3.3 顺序性

- 【说明】框架**不提供任何顺序保证**：投递是并发的，同一实体的多条消息也可能并行或乱序。
- 【强制】需要保序时由业务侧自行实现：在 Handler 内按 `entity_id` 串行，或用业务序列号 + 状态守卫拒绝乱序请求。
- 【禁止】依赖"消息按写入顺序被投递"——并发下不成立。

## 3.4 死信与对账

- 【强制】重试耗尽或不可重试的事件进入死信后，必须有**告警**与明确的**人工处置路径**。
- 【禁止】把死信当作正常终态，或依赖"它自己会好"。
- 【强制】关键链路必须有**对账**兜底。
- 【说明】对账是兜底，**不能替代**幂等与补偿机制——对账只负责发现不一致，不负责避免不一致。

# 四、补偿

- 【说明】补偿是**业务逆向操作**，不是数据库回滚：数据库回滚只能撤销未提交的本地事务，已提交的副作用只能靠业务补偿收敛。
- 【强制】补偿必须**幂等、可重复调用、允许 no-op**："查不到正向记录"不是报错的理由，按 §4.2 补写墓碑后返回成功。
- 【强制】占位表对 `bizKey` 必须有**唯一约束**——正向与补偿的互斥完全依赖它。
- 【强制】判定与回滚都必须用 CAS（`UPDATE ... WHERE key = ? AND status = ?` + 影响行数），禁止用 `FOR UPDATE` 代替判定。

> **术语：墓碑（tombstone）**——由补偿方补写的一条 `status = 失败` 的正向占位。
> 它标记该 `bizKey` 已终结、**不可再生**：之后同键的正向请求会在唯一键上冲突而被拒绝。
> 名字借自 LSM 存储的 tombstone（删除标记），语义相近：一条记录压住后续同名写入。
>
> 为什么用 CAS、为什么不用间隙锁：见 `../decisions/0004-compensation-idempotency-and-race.md`。

## 4.1 正向流程

```text
T1  独立事务，先提交（让补偿方立即可见）
    INSERT 正向占位 (bizKey, status = 处理中)
    ├─ 影响 1 行 → 继续 T2
    └─ 影响 0 行（唯一键冲突）→ 该 bizKey 已被占用，按现有状态处理：
         ├─ 处理中 → 重复请求，拒绝（或返回"处理中"）
         ├─ 成功   → 重复请求，幂等返回成功
         └─ 失败   → 已被补偿终结（墓碑），拒绝执行，返回明确错误

T2  业务事务（业务写入 + CAS 必须同一事务）
    执行业务写入（本地 DB）
    UPDATE 正向占位 SET status = 成功 WHERE bizKey = ? AND status = 处理中
    ├─ 影响 1 行 → 提交，正向成功
    └─ 影响 0 行 → 已被补偿抢占 → 回滚整个 T2（业务写入一并撤销），返回"已补偿"
```

- 【强制】T1 必须检查影响行数；**禁止** `INSERT IGNORE` / `ON CONFLICT DO NOTHING` 之后不看结果——那会让正向无视墓碑继续执行。
- 【强制】T2 的 CAS 与业务写入同事务；CAS 为 0 时回滚**整个事务**，不得只把状态改回去。
- 【说明】T1 独立提交的代价：占位表必须有状态字段，并配套僵尸回收（回收"处理中"必须走与 §4.2 相同的 CAS 路径，禁止直接删除或直改状态）。

## 4.2 补偿流程

```text
C1  补偿事务（① 判定 与 回滚 必须同一事务）
    ① INSERT 补偿占位 (key = RELEASE:{bizKey})
       └─ 冲突 → 补偿已执行过 → 返回成功（幂等）
    ② UPDATE 正向占位 SET status = 失败 WHERE bizKey = ? AND status = 处理中
       ├─ 影响 1 行 → 抢占成功：正向 T2 的 CAS 必然命中 0 行并回滚整个事务
       │              → 副作用不存在 → 无需回滚 → 提交，返回成功
       └─ 影响 0 行 → 继续 ③
    ③ SELECT status FROM 正向占位 WHERE bizKey = ?
       ├─ 成功   → 执行回滚（业务逆向操作）→ 提交，返回成功
       ├─ 失败   → 无需回滚 → 提交，返回成功
       └─ 无记录 → INSERT 正向占位 (bizKey, status = 失败)      ← 墓碑
                   ├─ 插入成功 → 提交，返回成功（正向此后无法开始）
                   └─ 唯一键冲突 → 正向刚提交占位 → 重读状态，按 ③ 重新判定
```

- 【强制】② 必须带 `status = 处理中`；抢到（1 行）意味着正向**不可能成功**，因此**不执行业务回滚**。
- 【强制】③ 无记录时必须**补写墓碑**（`status = 失败`），不得直接返回成功——否则"正向占位尚未提交"的窗口会让副作用在补偿之后落地。
- 【强制】③ 插入冲突时必须重新判定，不得提交半程结果（同一次补偿只允许一个终局）。
- 【说明】墓碑是**终态**：同一 `bizKey` 不可再次执行正向；需要重试时使用新的幂等键。
- 【说明】正向占位未提交时，补偿的 INSERT / UPDATE 会在唯一索引上等待：必须设置语句或锁等待超时，超时按**可重试**返回，既不能当成功也不能当失败。
- 【说明】"抢占成功即无需回滚"的前提是**副作用与 CAS 同事务**（§4.1 T2）；若副作用无法与本地事务同事务，本流程不适用，须由编排层 + 对账处理。

- 【强制】补偿必须防止"**迟到的正向请求**"重新生效：迟到的正向会撞上墓碑（T1 插入 0 行，状态为失败）而终止；业务自身仍须用状态守卫或版本号拒绝已进入补偿流程的写入。
- 【强制】无法自动收敛的补偿必须进入**人工处置**，禁止无限重试。

# 五、外部 MQ 消费

> 本节只约束**框架之外**的 MQ（Kafka / RocketMQ 等）消费侧；Outbox 自身的投递与重试见 §三。

- 【强制】消费者必须幂等（见 `idempotency.md`）。
- 【强制】消费失败必须有明确的重试、死信或补偿策略；且不得把"消息消费成功"等同于"业务一定成功"——
  下游副作用是否生效由业务补偿收敛（见 §四）。
- 【推荐】消息体使用稳定的事件模型（事件 ID、事件类型、业务主键、发生时间），而不是直接序列化数据库实体。

# 六、Checklist

改动涉及跨服务数据一致性时，逐条确认：

- [ ] 该处的一致性要求已显式声明（强一致 / 最终一致）？
- [ ] 事务内没有远程调用？
- [ ] 消息写入与业务写在同一本地事务？
- [ ] payload 只含最小上下文（业务主键），未整对象落库、无敏感信息？
- [ ] 消费端已建唯一约束：单条业务项用 `event_id`，列表 payload 已下沉到业务项粒度？
- [ ] 投递处理器 / 消费端已幂等？
- [ ] 可重试与不可重试已区分？
- [ ] 超时恢复阈值大于处理器最长执行时间？
- [ ] 需要保序时，已由业务侧串行（按 `entity_id`）或用状态守卫拒绝乱序？
- [ ] 失败补偿机制齐备（重试 + 死信 + 对账）？
- [ ] 补偿幂等、允许 no-op、能防迟到正向请求？
- [ ] 占位表对 `bizKey` 有唯一约束；正向插入检查了影响行数（0 行即终止，不得无视状态继续执行）？
- [ ] 正向的业务写入与"CAS 到成功"在同一事务（否则被抢占时无法回滚）？
- [ ] 补偿在"无正向记录"时补写了失败占位（墓碑），而不是直接返回成功？
- [ ] 死信有告警与人工处置路径？
