# 测试策略

> 定位：测试分层、单元测试与集成测试的边界、必须覆盖的行为、命名。
> 边界：幂等的测试语义见 `idempotency.md`；补偿与对账见 `reliability.md`；对象转换的断言见 `spring-boot.md` §3.5.5；数据库行为见 `database.md`。
>
> 规范级别：【强制】违反即视为代码问题；【推荐】默认遵守；【禁止】原则上不得使用；【说明】背景解释。

---

# 一、测试分层

- 【强制】核心业务规则必须有单元测试。
- 【推荐】纯业务领域对象应尽量**脱离 Spring 上下文**测试。
- 【推荐】Service 单元测试只 Mock **外部依赖**，不要 Mock 被测类本身。
- 【强制】数据库、Redis、MQ 等基础设施的关键行为必须有**集成测试**。
- 【推荐】使用 Testcontainers 验证真实数据库 / Redis 环境行为。
- 【禁止】只用内存数据库（如 H2）模拟真实数据库特性——JSON 列、部分索引、方言差异、锁与队列领取语义等**无法被替代**，这类测试会产生假绿灯。
- 【推荐】测试命名采用行为描述：`shouldCreateOrderWhenStockEnough`、`shouldRejectMatchWhenUserBlocked`。
- 【推荐】测试之间不得依赖执行顺序与共享可变状态。

---

# 二、必须覆盖的行为

【强制】以下行为必须有测试，不能只靠人工验证——它们的共同点是**出错时不会报错，只会静默产生脏数据**：

| 行为 | 为什么必须自动化 | 依据 |
| --- | --- | --- |
| 对象转换的关键字段 | 未映射字段静默通过，编译与运行都不报错 | `spring-boot.md` §3.5.5 |
| 写路径维护 `updated_at`（含逻辑删除） | 漏写不报错，数据库也不兜底 | `database.md` §8.3 |
| 软删除的查询与唯一约束 | 漏掉条件会读到已删数据；唯一约束可能形同虚设 | `database.md` §十 |
| 幂等：重复请求、并发重复请求 | 并发下的唯一性靠数据库约束，不靠"先查后插" | `idempotency.md` |
| 补偿：补偿幂等、允许 no-op、迟到的正向请求 | 竞态与重复补偿会导致数据反向损坏 | `reliability.md`、`../decisions/0004-compensation-idempotency-and-race.md` |
| 状态迁移的**非法路径被拒绝** | 绕过状态机的写入不会报错 | `java.md` §一 |
| 状态变更的并发行为（CAS 影响行数） | 影响行数为 0 的分支最易被忽略 | `database.md` §9.2 |

---

# 三、结构与命名

- 【推荐】测试方法名描述**行为与前提**，而不是描述实现（`shouldXxxWhenYyy`）。
- 【推荐】一个测试只验证一个行为；断言失败时能直接看出违反了哪条规则。
- 【推荐】测试数据构造集中在 Fixture / Builder，不散落在各测试方法中。
