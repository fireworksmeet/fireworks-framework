# 幂等

> 定位：所有**状态变更类写操作**（HTTP 接口、服务间调用、MQ 消费、定时任务、第三方回调）的幂等设计——落地形式、幂等键、幂等表、执行模型、返回约定、批量与清理。判据不是"有没有副作用"，而是"**重复执行会不会多做一次不该做的事**"；天然幂等的写操作（按 id 更新 / 删除、状态置为固定值）不要求调用方传幂等键，见 §3.2.1。
> 边界：**补偿**（三态判定、补偿占位、迟到正向请求）见 `reliability.md`；防篡改与防重放属入口层，本规范不涉及；表结构与索引写法见 `database.md`；分层与异常见 `spring-boot.md`、`api.md`。
>
> 规范级别：【强制】违反即视为代码问题；【推荐】默认遵守；【禁止】原则上不得使用；【说明】背景解释。

---

# 一、概念边界

三者解决的是**不同问题**，不可互相替代，禁止混为一谈。

| 问题 | 回答的是 | 手段 | 责任层 |
| --- | --- | --- | --- |
| **防篡改** | 请求内容有没有被改 | 签名 | 入口层（网关 / 代理） |
| **防重放** | 同一个**报文**会不会被重发 | 时间戳 + nonce + 签名 | 入口层（网关 / 代理） |
| **幂等** | 同一个**业务意图**会不会被执行多次 | 业务唯一键 / 幂等表 | 业务服务 |

- 【强制】防篡改与防重放属**入口层职责**，业务服务**禁止重复实现**（如再校验 nonce、再算签名）。
- 【强制】入口层的防重放**不能替代**业务幂等，因为二者粒度不同：
  - 防重放是**字节级**的——只拦住"同一报文的复制重发"；
  - 幂等是**业务意图级**的——用户连点两次按钮、客户端超时后重新发起，会产生**两个不同的报文**，入口层会全部放行。

# 二、落地形式与选择顺序

【强制】按 §2.1 → §2.2 → §2.3 的顺序选择（顺序即优先级），**能用业务唯一键就不要引入幂等表**。

## 2.1 优先使用业务唯一键

业务天然存在唯一标识时，直接在业务表建唯一索引，**零额外表**：

```sql
-- 业务语义上天然唯一：直接建唯一索引，零额外表
CREATE UNIQUE INDEX uk_order_main_provider_request
    ON order_main (provider, provider_request_id);
```

（软删除表的唯一约束写法随方言不同，见 ADR 0003）

典型类型：创建类、支付 / 资金类、回调类、状态流转类（具体业务场景清单由各业务仓库列明）。

## 2.2 无法用业务唯一键时使用幂等表

业务表没有自然唯一约束的"动作类"请求使用幂等表：

- "提交审核"、"发起认证"等重复提交会产生脏数据的动作；
- 客户端重试语义需要显式拦住的接口；
- 服务间调用需要去重的写操作。

## 2.3 最终底线

【强制】无论采用哪种形式，**幂等最终必须由数据库唯一约束保证**，禁止仅靠应用层 `if` 判断（应用层判断在并发下必然出错）。

# 三、幂等表设计

【强制】每个业务服务 / 模块维护**自己的**幂等表，**禁止跨服务共用一个幂等表**。

表名：`<业务实体>_idempotent` 或 `idempotent_record`（同库内唯一即可）。

> 下列 DDL 以 **PostgreSQL** 为基线；MySQL 差异集中列在 §3.1.4。

## 3.1 表结构

### 3.1.1 完整形态（跨事务 / 异步场景）

```sql
CREATE TABLE order_idempotent (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY,
    CONSTRAINT pk_order_idempotent PRIMARY KEY (id),
    idempotent_key  VARCHAR(128) NOT NULL,
    biz_type        SMALLINT     NOT NULL,
    status          SMALLINT,
    result_snapshot JSONB,
    expired_at      TIMESTAMPTZ  NOT NULL,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP
);

COMMENT ON COLUMN order_idempotent.idempotent_key  IS '幂等键，由发起方生成，唯一标识一次业务意图';
COMMENT ON COLUMN order_idempotent.biz_type        IS '业务类型：10-下单，20-取消，...';
COMMENT ON COLUMN order_idempotent.status          IS '幂等状态（仅跨事务时使用）：10-处理中，20-成功，30-失败';
COMMENT ON COLUMN order_idempotent.result_snapshot IS '请求最终结论快照：成功存结果摘要，失败存错误码，处理中为 NULL';
COMMENT ON COLUMN order_idempotent.expired_at      IS '可被清理的时间点；清理任务仅删除已过期的记录';

CREATE UNIQUE INDEX uk_order_idempotent_key ON order_idempotent (idempotent_key);
CREATE INDEX idx_order_idempotent_expired_at ON order_idempotent (expired_at);
```

### 3.1.2 简化形态（同步 + 同事务，默认推荐）

同步同事务场景下 `status` / `result_snapshot` 均无意义（记录会随业务回滚消失），仅保留清理所需的 `expired_at`：

```sql
CREATE TABLE order_idempotent (
    id             BIGINT GENERATED BY DEFAULT AS IDENTITY,
    CONSTRAINT pk_order_idempotent PRIMARY KEY (id),
    idempotent_key VARCHAR(128) NOT NULL,
    biz_type       SMALLINT     NOT NULL,
    expired_at     TIMESTAMPTZ  NOT NULL,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at     TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE UNIQUE INDEX uk_order_idempotent_key ON order_idempotent (idempotent_key);
CREATE INDEX idx_order_idempotent_expired_at ON order_idempotent (expired_at);
```

### 3.1.3 字段说明

- 【强制】`expired_at` 为**必填**（`NOT NULL`），由**业务代码计算**后作为参数传入（如 `expiredAt = Instant.now().plus(...)`），禁止在 SQL 中计算；保留期的取值约束见 §8.1。
- 【说明】`status` **默认不加**，仅在「幂等占位与业务写入不在同一事务」时追加，见 §3.3。
- 【说明】`result_snapshot` 仅在跨事务 / 异步场景追加，与 `status` 强绑定，见 §3.4。
- 【禁止】`biz_id` 不进幂等表：同步同事务场景业务回滚时记录一并回滚，无需追溯主键；跨事务场景需要保存的是"最终结论"（`result_snapshot`），而不是业务主键。
- 【说明】时间字段的"计算位置"由语义决定：技术时间戳（`created_at` / `updated_at`）用数据库当前时间；业务时间（`expired_at`）必须由应用计算。

### 3.1.4 MySQL 差异

| 项 | PostgreSQL | MySQL |
| --- | --- | --- |
| 自增主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BIGINT NOT NULL AUTO_INCREMENT`（在 `CREATE TABLE` 内声明 `PRIMARY KEY`，或额外建索引） |
| 快照列 | `JSONB` | `JSON` |
| 时间列 | `TIMESTAMPTZ` | `TIMESTAMP`（见 ADR 0002 的 2038 约束与替代方案） |
| 列注释 | `COMMENT ON COLUMN ...` | `CREATE TABLE` 内联 `COMMENT '...'` |

## 3.2 幂等键（`idempotent_key`）

### 3.2.1 归属原则

- 【强制】幂等键的**语义与格式由提供该业务能力的服务（下游）定义**，调用方仅在**下游明确要求**时传递。
- 【强制】天然幂等的接口（按 id 更新、按 id 删除、查询、状态置为固定值）**不得**要求调用方传幂等键。
- 【强制】需要幂等键时，作为**接口入参 DTO 的显式可选字段**（配合接口文档说明），**不使用全局隐式 Header**：
  - 隐式 Header 对所有接口出现，容易漏传，且无法表达"哪些接口需要"；
  - 放在 DTO 中，接口契约会明确声明"此接口需要幂等键"，做到谁需要谁声明。

```java
@Data
public class OrderCreateRequest {
    @Schema(description = "幂等键；由客户端生成，服务端会话内唯一")
    private String idempotentKey;

    // ... 其他业务字段
}
```

### 3.2.2 生成方式与组合兜底

- 【强制】幂等键由**客户端 / 调用方生成**（如 UUID），用于标识"第几次业务意图"。
- 【强制】服务端**不签发、不信任**客户端传来的值，必须**按自己的维度重新组合**后再使用：

```text
key = {服务端维度}:{业务动作}:{客户端值}
例如 key = {userId}:order:create:{clientUuid}
```

【说明】组合的价值是**防串扰**（防止客户端乱传的值侵入其他用户 / 其他业务的幂等空间），**不是防伪造**。

### 3.2.3 能力边界（重要）

- 【说明】幂等键只能拦住"同一个业务意图被重复执行"，**不构成安全边界**：客户端可以更换 key 重复提交，幂等无法阻止。
- 【禁止】把"服务端签发幂等 Token"包装成安全机制——签发接口本身可被任意调用，**不产生任何防御价值**，只增加一次网络往返与一份状态存储。
- 【说明】恶意重复提交须通过**限流、业务规则约束、唯一业务约束**解决，不由幂等承担。

### 3.2.4 粒度

【强制】幂等键必须下沉到**业务项粒度**，禁止用消息级 / 请求级标识代替：

| 场景 | 幂等键 | 说明 |
| --- | --- | --- |
| HTTP 单笔业务 | `order:create:{orderNo}` | 优先使用业务标识 |
| 客户端重复提交 | `{userId}:{bizType}:{clientUuid}` | 见 §3.2.2 组合兜底 |
| **MQ 批量消费** | `order:create:{orderNo}`（业务项级） | **`msgId` 只能作任务表的批次标识，不得作幂等键**（见 §6.1） |
| 第三方回调 | `pay:{provider}:{providerRequestId}` | 优先使用第三方流水号 |

### 3.2.5 通用约束

- 【强制】幂等键必须能**唯一标识一次业务意图**，长度不超过 128 字符。
- 【推荐】采用 `{业务域}:{动作}:{业务标识}` 结构，便于排查。
- 【禁止】把可能重复的值**单独**用作幂等键（如 `userId`、`timestamp`、纯随机数）；至少须与服务端维度组合（见 §3.2.2）。

## 3.3 `status`：仅在跨事务时追加

【强制】`status` **默认不要**。判断标准是「幂等占位与业务写入能否在同一个数据库事务内原子回滚」：

| 场景 | 需要 `status` | 说明 |
| --- | --- | --- |
| 幂等占位 + 业务写入**同一事务**（纯同步、无外部副作用） | ❌ | 业务失败回滚，幂等记录一并回滚，事务外只有"成功 / 不存在" |
| 幂等占位**独立提交**，业务写入在其后 | ✅ | 必须能表达"占位了但没做完"的中间态 |
| 流程中含**不可回滚的外部动作**（第三方支付、发 MQ） | ✅ | 外部动作不可回滚，"同事务"不成立 |

需要时按下述定义追加：

```sql
status SMALLINT NOT NULL DEFAULT 10
-- 10-处理中，20-成功，30-失败
```

状态机为三态，**不引入"补偿中"等中间状态**：

```text
10-处理中  →  20-成功（终态）
           ↘  30-失败（终态，含被补偿抢占后作废）
```

- 【说明】不引入"补偿中"的原因：一旦引入就必须再引入"已补偿"终态，否则会制造新的僵死状态；"是否已被回滚"应由**业务数据**表达，幂等表无需重复记录（推导见 `../decisions/0004-compensation-idempotency-and-race.md`）。
- 【强制】引入 `status` 后必须同时设计**僵尸记录回收机制**：超时仍停留在"处理中"的记录必须能被识别与处理（定时任务标记失败或清理），否则业务会永久锁死。
- 【强制】状态流转必须使用 **CAS**（`WHERE status = 期望前置状态`）并按影响行数判定，禁止裸 `UPDATE`；CAS 的 `UPDATE` 与业务副作用必须在**同一事务**内提交。终态不可再被改写。

---

## 3.4 `result_snapshot`：跨事务场景的结果回放

- 【强制】`result_snapshot` **仅在跨事务 / 异步场景使用**，与 `status` 成对出现。
- 【说明】存在意义：跨事务场景下不保存业务主键（无指针可回查业务表），而重复请求要求"快速返回结果"，因此结果必须**自包含地**存在幂等表中。

【强制】`status` 与 `result_snapshot` 的绑定关系（重复请求返回什么见 §5）：

| `status` | `result_snapshot` |
| --- | --- |
| 处理中 | 必须为 `NULL` |
| 成功 | 必须有值 |
| 失败 | 必须有值（错误码） |

【强制】快照内容遵循：

- 存**结论摘要**，不存完整业务对象——只保存调用方重试时真正需要的少量字段，形如 `{"orderNo":"xxx","status":20}`；
- 禁止与业务表字段同构，避免形成第二数据源与一致性负担；
- 必须在表注释或接口文档中写明快照 schema；
- 属于 `database.md` 允许的"结果 / 第三方响应快照"用途，不违反"核心业务字段禁放 JSON"。

# 四、两种执行模型

## 4.1 同步 + 同事务（默认，推荐）

【强制】这是默认模型，依赖「业务异常抛出 → 事务回滚 → 幂等记录一并回滚」。

```java
@Transactional
public void createOrder(OrderCreateRequest request, String idempotentKey) {
    // 1. 占位：插入失败（唯一键冲突）说明已处理过，直接抛业务异常
    BizAssert.isTrue(
        orderIdempotentRepository.insertIgnore(idempotentKey, OrderBizType.CREATE, expiredAt) == 1,
        REPEAT_SUBMIT);

    // 2. 业务写入（与占位同一事务）
    orderRepository.insert(order);

    // 3. 如有远程调用 / 发消息，必须在事务提交后异步执行（见 reliability.md）
}
```

占位 SQL（**按影响行数判定：1 = 首次执行，0 = 重复请求**）——方言写法不同：

```sql
-- PostgreSQL
INSERT INTO order_idempotent (idempotent_key, biz_type, expired_at) VALUES (:key, :bizType, :expiredAt)
ON CONFLICT (idempotent_key) DO NOTHING;

-- MySQL
INSERT IGNORE INTO order_idempotent (idempotent_key, biz_type, expired_at) VALUES (:key, :bizType, :expiredAt);
```

- 【强制】`expired_at` 必须在占位时**一次性写入**，不得留空、不得事后补写。
- 【强制】**禁止在幂等占位之后 `catch` 业务异常并正常返回**——那会留下悬挂的幂等记录，导致该业务意图**永久无法再执行**：

```java
// 禁止
public void createOrder(...) {
    repository.insertIgnore(...);
    try {
        doCreate(...);
    } catch (Exception e) {
        log.error("failed", e);   // ❌ 异常被吞，事务不回滚，幂等记录留下
        return;
    }
}
```

## 4.2 异步 / 跨事务

【强制】适用于"占位独立提交"或"流程中含不可回滚外部动作"的场景。

- 【强制】必须追加 `status`（§3.3）与 `result_snapshot`（§3.4），并配套僵尸记录回收机制；
- 【强制】流程结束时必须**回写终态**：`status` 落终态的同时写入 `result_snapshot`；
- 【强制】重复请求的返回约定必须明确（见 §5）；
- 【推荐】若需要"部分成功只重试失败项"，应当**另建任务表 / 消息表**，不要用幂等表承担（见 §6）。

```sql
-- 终态回写：AND status = 10 保证终态只被写入一次，重复回写不生效
UPDATE order_idempotent
SET status = :status,
    result_snapshot = :resultSnapshot,
    updated_at = CURRENT_TIMESTAMP
WHERE idempotent_key = :key
  AND status = 10;
```

# 五、重复请求的返回约定

【强制】必须按模型明确返回值，**禁止"返回空"**：

| 模型 | 重复请求返回 | 说明 |
| --- | --- | --- |
| 同步 + 同事务 | **返回业务错误**（如"重复提交"） | 语义清晰：上一次已成功，本次拒绝 |
| 异步 / 跨事务 | 按 `status` 区分：处理中 → 返回"处理中"；成功 → **返回 `result_snapshot` 内容**；失败 → 返回 `result_snapshot` 中的失败结论 | 禁止把"处理中"误报为"成功" |

【强制】异步场景的终态必须直接返回 `result_snapshot`，**禁止再回查业务表**——否则 `result_snapshot` 失去存在意义，且业务表数据可能已被清理。

---

# 六、与"重试"的职责边界

【强制】幂等表只负责**防重复**，不负责**驱动重试**：

| 关注点 | 归属 |
| --- | --- |
| 请求级重试（同步调用超时重发、用户重复点击） | 幂等表（保证重试不重复执行） |
| 任务级重试（MQ 消费失败重投、定时补偿、批量部分失败） | **消息表 / 任务表** |

【强制】需要"精确只重试失败项"的场景，必须保留失败态记录，这属于**任务表**职责，应单独建表，禁止把幂等表当任务表使用。

## 6.1 MQ 消费的幂等键粒度

- 【强制】消息体为**单条业务项**时，幂等键用该业务项标识（如 `order:create:{orderNo}`）。
- 【强制】消息体为**列表**（一条消息含 N 个业务项）时：
  - **禁止**用 `msg:{msgId}` 作幂等键——它只标识"整条消息"，一旦部分成功部分失败，重试时整条消息会被幂等表拦住，失败项**永远无法补偿**；
  - **必须**下沉到业务项粒度：用业务标识（如 `orderNo`）或 `msg:{msgId}:{seq}` 组合；
  - `msgId` 的正确用途是作为**任务表的批次标识**（负责"只重投失败的项"），与幂等表分工协作。

```text
幂等表：按业务项去重（order:create:{orderNo}）
任务表：记录 msgId + seq 的处理状态，负责"只重投失败的项"
```

# 七、批量场景

## 7.1 抢坑位并拿到可执行集合

多条业务项一次占位时，必须能区分"本次新插入"与"早已存在"。

**PostgreSQL** —— 一条 SQL 用 `RETURNING` 直接拿到：

```sql
INSERT INTO order_idempotent (idempotent_key, biz_type, expired_at)
VALUES (:key1, :bizType, :expiredAt), (:key2, :bizType, :expiredAt)
ON CONFLICT (idempotent_key) DO NOTHING
RETURNING idempotent_key;
```

**MySQL** —— 无 `RETURNING`，用**批次标记列**：

```sql
-- ① 带批次标记写入（batch_token 由本次调用生成）
INSERT IGNORE INTO order_idempotent (idempotent_key, biz_type, expired_at, batch_token)
VALUES (:key1, :bizType, :expiredAt, :batchToken), (:key2, :bizType, :expiredAt, :batchToken);

-- ② 回查本次批次真正插入成功的 key（batch_token 需建索引）
SELECT idempotent_key FROM order_idempotent WHERE batch_token = :batchToken;
```

```java
// 返回的 = 本次真正插入成功的 key
Set<String> executable = new HashSet<>(insertedKeys);

// 按 key 匹配可执行集合，未匹配到的 = 已存在 = 跳过
for (Item item : items) {
    if (executable.contains(item.key())) {
        doProcess(item);
    }
}
```

- 【强制】`RETURNING` / 回查结果的**顺序不保证与入参顺序一致**，必须**按 key 匹配**，禁止按下标对应。
- 【强制】禁止**不带批次标记**地按 key 回查来区分新旧——那样的查询结果**同时包含新插入与早已存在的记录**，无法区分（MySQL 必须带 `batch_token` 条件，见上）。
- 【说明】MySQL 的批次标记列是"本次批次的显式标识"，与"无业务语义的随机值"不同；PostgreSQL 已有 `RETURNING`，不得再用标记列绕行。

## 7.2 事务边界

- 【强制】批量场景按子批次（如每 50~200 条）独立事务提交，禁止"一次批量占位 + 批量写业务"构成大事务。
- 【说明】子批次独立提交后，重试时靠幂等键天然跳过已成功项，无需应用层手动剔除。

## 7.3 幂等键的批次隔离

- 【强制】若批量项以"批次 + 序号"标识，幂等键必须包含**批次标识**（如 `{batchNo}:{seq}`），否则跨批次会互相冲突。
- 【说明】列表消息的幂等键粒度（业务标识优先，其次 `msg:{msgId}:{seq}`）见 §6.1。

# 八、记录清理

【强制】幂等表必须设计清理机制，防止无限膨胀。清理**以 `expired_at` 为唯一基准**，不使用 `created_at` / `updated_at`。

## 8.1 保留期与 `expired_at`

- 【强制】`expired_at` 由**业务代码计算**后作为参数传入，禁止在 SQL 中用 `CURRENT_TIMESTAMP + INTERVAL '...'` 计算——业务时长必须外置、可单测，且 SQL 计算受会话时区影响。
- 【强制】保留期**不集中定义**，由各业务自行决定，但必须满足：
  - 保留期需**远大于**该业务的可重试窗口（客户端重试、调用方重试、人工补单）；
  - 保留期必须有明确依据（业务上"不可能再重放"的时间点），并在表注释或业务文档中说明；
  - 【禁止】保留期小于客户端重试窗口——会导致旧请求重放穿透，幂等失效。
- 【说明】`expired_at` 一经写入即固定，**不随状态变更刷新**（它表达"何时可清理"，与业务状态无关），因此无需在终态回写时维护。

## 8.2 清理任务

- 【强制】清理任务必须**幂等 + 多实例安全**（分布式锁或任务分片，见 `spring-boot.md`）。
- 【强制】**分批删除**，每批独立提交，禁止一次性大事务。
- 【强制】记录开始时间、结束时间、删除数量、失败数量。
- 【强制】清理条件必须**排除未终结的记录**：

```sql
-- 异步 / 跨事务场景：必须排除"处理中"
DELETE FROM order_idempotent
WHERE id IN (
    SELECT id FROM order_idempotent
    WHERE expired_at < CURRENT_TIMESTAMP AND status <> 10
    ORDER BY id LIMIT 10000
);
```

```sql
-- 同步 + 同事务场景：无 status，记录存在即代表已完成，可直接清理
DELETE FROM order_idempotent
WHERE id IN (
    SELECT id FROM order_idempotent
    WHERE expired_at < CURRENT_TIMESTAMP
    ORDER BY id LIMIT 10000
);
```

【说明】"处理中"的记录由**僵尸回收机制**负责（§3.3），不是清理任务的职责——清理任务只处理"已终结且已过期"的记录。

## 8.3 索引与大规模优化

- 【强制】`expired_at` 必须建索引，否则清理任务全表扫描。
- 【推荐】数据量极大时，按创建时间做**分区**，用 `DROP PARTITION` 替代 `DELETE`，避免 `DELETE` 造成的索引膨胀与 VACUUM / 碎片压力（分区语法按数据库方言）。

# 九、评审清单

写操作涉及幂等时逐条确认。**❌ 后是该条最典型的错误做法**；规则本身在前文对应章节已展开，此处只给判定。

## 9.1 落地形式

- [ ] 该写操作是否评估过幂等，确认它不属于天然幂等（按 id 更新 / 删除、查询、状态置固定值）？
- [ ] 是否优先尝试业务唯一键（❌ 能用唯一键却引入幂等表）？
- [ ] 幂等表是否落在正确的业务服务（❌ 跨服务共用一张幂等表）？
- [ ] 是否有数据库唯一约束兜底（❌ 仅靠应用层 `if` 判断）？
- [ ] 防篡改 / 防重放是否交给入口层（❌ 业务服务重复实现 nonce、签名），且没有把入口层防重放当作业务幂等（❌ 认为二者可互相替代）？

## 9.2 幂等键

- [ ] 是否由客户端 / 调用方生成？
- [ ] 服务端是否按自身维度重新组合（❌ 直接信任客户端值；❌ 用 `userId` / `timestamp` / 随机数单独作键）？
- [ ] 是否作为入参 DTO 的显式可选字段（❌ 全局隐式 Header）？
- [ ] 天然幂等的接口是否**没有**要求传幂等键？
- [ ] 是否没有把"服务端签发幂等 Token"包装成安全机制（❌ 签发接口本身可被任意调用，只多一次往返与一份状态）？
- [ ] 长度是否 ≤ 128，且能唯一标识一次业务意图？
- [ ] 列表消息是否下沉到业务项粒度（❌ 用 `msgId` 作键）？
- [ ] 批量项是否带批次标识 `{batchNo}:{seq}`（❌ 跨批次互相冲突）？

## 9.3 表结构与执行模型

- [ ] `expired_at` 是否必填、由应用计算传入（❌ 在 SQL 中用 `CURRENT_TIMESTAMP + INTERVAL` 计算）？保留期是否远大于重试窗口（❌ 小于重试窗口）？
- [ ] 是否**默认没有** `status`，只在占位与业务写入不同事务、或含不可回滚外部动作时才加（❌ 无条件加）？
- [ ] 加了 `status` 时是否配套僵尸记录回收，且状态流转使用 CAS 并按影响行数判定（❌ 裸 `UPDATE`）？
- [ ] 跨事务场景是否成对使用 `status` 与 `result_snapshot`，并说明快照 schema（❌ 存成完整业务对象形成第二数据源）？
- [ ] 重复请求的返回约定是否明确、错误码是否已定义（❌ 返回空；❌ 把"处理中"误报为成功）？异步场景是否直接返回快照（❌ 回查业务表）？
- [ ] 是否避免在占位后 `catch` 业务异常并正常返回（❌ 留下悬挂记录，该业务意图永久无法再执行）？

## 9.4 批量与清理

- [ ] 批量是否用 `RETURNING`（PG）/ 批次标记列（MySQL）拿到可执行集合，并按 key 匹配（❌ 按下标对应；❌ 不带批次标记回查）？
- [ ] 子批次是否独立事务提交（❌ 一次批量占位 + 批量写业务构成大事务）？
- [ ] 清理是否以 `expired_at` 为唯一基准（❌ 用 `created_at`）、分批提交、排除"处理中"（❌ 误删处理中）、幂等且多实例安全？
- [ ] "精确只重试失败项"是否交给任务表 / 消息表（❌ 把幂等表当任务表）？
- [ ] 幂等表是否有清理机制（❌ 无清理导致无限膨胀）？
