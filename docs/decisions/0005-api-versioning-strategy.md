# 0005. 接口版本演进：原地兼容优先，内部接口协同改造

- **状态**：已接受
- **日期**：2026-09-20

## 背景

API 路径**首版不带版本段**（`/order/create`，见 `conventions/api.md` §1.2），只有出现无法兼容的破坏性变更时才在首段引入 `/v2`。但**版本演进与兼容规则未定义**，导致：不清楚什么改动需要升版本；不清楚字段能否删除、重命名、改语义；不清楚废弃流程与观察期；内部接口与对外接口是否同样处理没有结论。结果是要么不敢动接口，要么改动无据可依。

关键约束：**存在无法强制升级的客户端**（移动端应用商店不允许强制升级），服务端可能长期面对任意历史版本的调用，兼容窗口**不能用"发布版本数"衡量**。

## 决策

1. **原地兼容演进优先，升版本是最后手段**：旧路径（无版本段）与 `/v2` 并存意味着同一份业务逻辑维护两套（代码、测试、文档），且所有调用方要分批改造。

2. **兼容性以"调用方不改代码能否继续工作"判定**：这是唯一可被逐条判定、不产生争论的标准，取代"改动大小""是否影响语义"等主观标准。

3. **破坏性变更优先用兼容方式承载**：加新字段并保留旧字段过渡，而非直接改旧字段（做法见 `conventions/api.md`）。

4. **废弃走三段式：标记废弃 → 观察期确认无调用方 → 删除**；观察期以**绝对时间**计，**不得以发布版本数计**（不可强制升级的客户端会长期存在）。具体时间下限由各业务按客户端升级能力定档。

5. **内部接口不通过 URL 版本号演进，改用协同改造**：调用方可控，故不需长期并存多版本；但"可控"不等于"可单方面破坏"，必须同批次同步改造。内外接口的本质差异在**调用方是否可控**。

6. **枚举演进依赖预留间隔**：ADR 0001 的 `code` 编排本身就是为演进准备的，因此"新增枚举值"属兼容变更；前提是调用方对未知值必须降级展示。

> 可执行细则见 `conventions/api.md`：路径与版本段约定在 §1.2，判定表、兼容做法、废弃流程与 Checklist 在 §十。

## 理由

1. **维护成本**：多版本并存 = 多套代码 / 测试 / 文档 + 所有调用方分批改造，成本随版本数迅速膨胀；若每次改动都升版本，版本号会膨胀到无人敢改。
2. **判据必须可执行**：只有"调用方不改代码能否继续工作"能逐条判定；其余标准都会陷入争论。
3. **内外有别**：调用方可控性不同，决定了"协同改造"与"版本隔离"是两种正确解，而非同一规则的不同参数。

## 后果

- **正面**：明确"何时该升版本"；破坏性变更有可执行的过渡路径；内部接口演进方式明确。
- **注意**：不可强制升级的客户端意味着废弃字段会**长期存在**，需确认这一成本可接受。
- **注意**：观察期的"确认无调用方"依赖日志 / 监控能力（见 `conventions/observability.md`）。
- **注意**：内部接口的"全仓库搜索调用方"是**人工纪律**，需纳入 Code Review 检查项。
- **注意**：本规则**自接口首次对外发布起生效**；未上线阶段的调整不受约束。
