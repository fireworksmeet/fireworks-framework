# 0004. 补偿场景的幂等与竞态处理（CAS 取代 FOR UPDATE）

- **状态**：已接受
- **日期**：2026-09-17

## 背景

分布式业务（如"下单 → 扣库存 → 失败补偿"）存在一类隐蔽缺陷：

1. 正向操作（扣减库存）执行超时，调用方**无法确定它是否成功**；
2. 调用方发起补偿，补偿方查询"是否已扣减"时**查不到记录**；
3. 补偿方据此判定"未执行、无需回滚"并返回成功；
4. 而正向事务在补偿提交**之后**才真正提交 → **库存被扣但未被回滚（多扣）**。

根因：**默认隔离级别（`READ COMMITTED`）下，补偿查询看不到"已执行但未提交"的正向事务**。此时"查不到"不等于"未执行"，而是"结果不确定"。

曾考虑的 `SELECT ... FOR UPDATE` 方案有两个死结：

- `FOR UPDATE` 只能锁**已存在**的行，**无法锁住"尚不存在的行"**——而"查不到"正是本题的核心场景；
- 能锁"不存在的间隙"的是 MySQL InnoDB 的**间隙锁**，属**方言特有**机制；PostgreSQL 下无等价能力（`SERIALIZABLE` 依赖谓词锁，需处理序列化失败重试，复杂且不可移植）。

## 决策

### 1. 并发控制统一用 CAS，不用锁

【强制】补偿与正向之间的竞态，用数据库 **CAS**（`UPDATE ... WHERE key = ? AND status = ?` + 判断影响行数）收敛，**禁止**依赖 `FOR UPDATE` 或隔离级别特性。

### 2. 补偿判定：禁止把"查不到"当作"未执行"

【强制】按观察到的状态判定，**"无记录"属于不确定，不属于未执行**：

| 观察 | 判定 | 动作 |
| --- | --- | --- |
| 无正向记录 | **不确定**（正向的占位可能尚未提交） | 补写"失败"占位（墓碑），见决策 5 |
| 处理中 | 不确定（正向可能马上提交成功） | CAS 抢占；**抢到即无需回滚** |
| 成功终态 | 确定已执行 | 执行回滚 |
| 失败终态 | 确定未执行（或已作废） | 无需回滚 |

【说明】抢占成功之所以不用回滚：正向的"业务写入 + CAS 到成功"在同一事务（决策 6），它被抢占后 CAS 命中 0 行，必须回滚整个事务，业务写入随之消失。

【术语】**墓碑**（tombstone）：补偿方补写的 `status = 失败` 正向占位，标记该 `bizKey` 已终结、**不可再生**——之后同键的正向请求会在唯一键上冲突而被拒绝。名字借自 LSM 存储的删除标记（一条记录压住后续同名写入）；完整定义见 `conventions/reliability.md` §四。

### 3. 正向操作先占位并独立提交，且必须检查插入结果

【强制】正向先写入占位（独立事务提交），使占位对补偿方**立即可见**，消灭"完全不可见"的窗口。

【强制】插入必须检查影响行数，0 行时按现有状态终止，不得继续执行：

| 现有状态 | 处理 |
| --- | --- |
| 处理中 | 重复请求，拒绝（或返回"处理中"） |
| 成功 | 重复请求，幂等返回成功 |
| 失败 | 已被补偿终结（墓碑），拒绝执行并返回明确错误 |

【禁止】`INSERT IGNORE` / `ON CONFLICT DO NOTHING` 之后不看结果——正向会无视墓碑继续执行副作用，整个机制失效。

代价与配套：占位独立提交后，占位表必须引入状态字段，并配套**僵尸记录回收**；回收"处理中"必须走与补偿相同的 CAS 路径，禁止直接删除或直改状态。

### 4. 补偿自身也必须占位

【强制】补偿在占位表中以**含动作语义的独立键**占位（如 `RELEASE:{bizKey}`）：

- 占位失败 → 补偿已执行过 → **静默返回成功**（重复发起补偿不应报错）；
- 占位成功 → 继续执行补偿逻辑。

【强制】补偿占位与回滚副作用**必须在同一事务内提交**；禁止"先独立提交占位，再执行回滚"——那会制造"占位已提交但回滚未执行"的新僵死态。

### 5. 无正向记录时，补偿方补写"失败"占位（墓碑）

【强制】补偿读到无记录时，必须在**同一补偿事务**中插入 `(bizKey, status = 失败)`，把"不确定"变成"正向不可能开始"。

【强制】插入若唯一键冲突，说明正向刚提交占位，必须重读状态重新判定，不得提交半程结果。

【说明】这是"查不到"的唯一正确解法：不猜结果、不报错让调用方重试、也不放过可能的副作用。代价是墓碑使 `bizKey` 进入终态，重试必须换新的幂等键。

### 6. 正向落终态的 CAS 失败必须回滚自身业务数据

【强制】正向操作将状态推进到成功终态的 CAS 若影响行数为 0，说明补偿已抢占，**正向必须回滚自身已写入的业务数据**；该 CAS 与业务副作用必须同事务。

### 7. 状态机三态收敛，不引入"补偿中"

```text
处理中  →  成功（终态）
        ↘  失败（终态，含"被补偿抢占后作废"）
```

【说明】不引入"补偿中"状态的原因：一旦引入就必须再引入"已补偿"终态，否则会制造新的僵死状态，需要再设计一套回收机制。而"是否已被回滚"应由**业务数据**与补偿占位表达，占位表无需重复记录。

## 理由

1. **数据正确性优先**：多扣/少扣属于资金级错误，必须从机制上消除，不能依赖"大概率不会同时发生"。
2. **CAS 优于锁**：把竞态收敛为一次数据库原子操作——无跨事务可见性问题、无锁等待、无隔离级别依赖。
3. **可移植**：CAS 在所有关系型数据库语义一致，不受 PostgreSQL / MySQL 隔离机制差异影响。
4. **与幂等规范自洽**：占位独立提交后引入状态字段，正是幂等表既有的设计方向。

## 后果

- **正面**：消除"补偿误判导致的数据不一致"；正向与补偿的竞态由数据库保证唯一赢家。
- **注意**："无记录 → 补写墓碑"让 `bizKey` 成为**终态**：同一业务意图不可再次执行，重试必须换新的幂等键。
- **注意**：正向占位的插入未提交时，补偿的 INSERT / UPDATE 会在唯一索引上等待；必须设置语句或锁等待超时，超时按**可重试**返回，不得当作成功或失败。
- **注意**：占位独立提交意味着状态字段成为必需品，**清理任务必须排除"处理中"记录**，否则会清掉正在执行的占位。
- **注意**：占位语义在方言上写法不同——PostgreSQL 用 `ON CONFLICT DO NOTHING`，MySQL 用 `ON DUPLICATE KEY UPDATE` 或显式捕获唯一键冲突，语义一致：**占位失败即已执行过**。**不要用 `INSERT IGNORE`**：它会把截断等其它错误一并吞掉，导致"以为占位成功"。
- **注意**：本决策只覆盖**副作用与 CAS 位于同一本地事务**的场景；副作用是远程调用时无法靠本地回滚撤销，需要编排层补偿与对账，框架不提供分布式事务引擎。
- **注意**：若业务允许"最终一致"，可用对账任务兜底，但**不能替代**上述机制。
